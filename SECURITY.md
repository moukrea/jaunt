# Security model — unaudited beta

jaunt provides a full shell under the host account. There is no filesystem sandbox or read-only role: an authorized device can act as that user. Do not run the host with privileges that remote devices do not need.

## What is protected

Commands, output, files, and clipboard data are encrypted between the browser and host. The relay sees network addresses, rooms, presence, packet sizes and timing, and ephemeral public keys. It does not hold pairing or device secrets. The channel is authenticated by a random 256-bit secret, with ephemeral ECDH and AES-GCM. The protocol specification is kept with the source, which is private.

Direct link (on by default): once a device is connected through the relay, it and the host try to reach each other over a WebRTC data channel, and carry the same encrypted channel there while it works. Nothing about the content changes: the data channel carries the frames the relay would (sealed by the same jaunt channel, same keys and counters), so DTLS is an additional layer, not the protection. The offer and the answer, with each side's DTLS certificate fingerprint, and the candidates either side sends after them, travel inside the end-to-end encrypted channel, so the relay can neither read nor replace them, and each side's handshake fails unless the certificate presented matches the fingerprint the other side signalled: the relay cannot put itself in the middle of a direct link. What it changes is who learns which network addresses:
- The device and the host learn each other's candidate addresses. The host offers every address of its interfaces that are up (LAN, VPN, container bridges in use, a public IPv6 address) and its public address as a STUN server sees it; with "Same network only" it offers only its private addresses (RFC 1918, CGNAT 100.64/10 as VPN overlays use, IPv6 unique local and link-local), asks no STUN server and keeps a direct link only when the device's address is private too; browsers hide their local addresses behind random mDNS names, so the host learns a device's public address (and, on a LAN, its local one through the connection itself). Paired devices take part (a linked host never does), and they can already run commands on the host. A guest's device and a public link's visitor (below) make direct links too and cannot run commands: the host offers them only the address its traffic to the Internet leaves from, per family (on most networks its LAN address, which its own TURN server's relayed address shows anyway, and its IPv6 one) and its public address (STUN and the router's ports), never its other networks (VPN overlays, container bridges, another LAN, link-local, unique local or other IPv6 addresses); a host with no route to the Internet at all offers them its addresses as to a device. The host's log and `jaunt status` name a link's stage (same network, through NATs, relayed, or the relay) and candidate types, never an address (aioice's own lines, which name them, are kept out of the log); the host keeps the address each device saw it from in memory only, to tell the stage.
- The desktop and Android apps also send the host the addresses of their own network interfaces (at most four, private, shared or global; `addresses` in `direct.offer`, docs/PROTOCOL.md), inside the encrypted channel with the offer, because a browser hides them behind mDNS names that a host behind a firewall cannot resolve; a plain browser sends none. Only the paired host learns them (a linked host, a guest share's host and the relay never do), it uses them for connectivity checks toward the device and keeps them in memory with the link, and its log and `jaunt status` never name an address. A device on a network the host can then reach is checked by the host: a host asked this way sends STUN requests to at most eight addresses per link, each at a port the device itself offered.
- STUN servers (default `stun:stun.cloudflare.com:3478` and `stun:stun.l.google.com:19302`, configurable per host, none with "Same network only") learn the public address and port of the host and of each device when they look for a direct link, and when (the host asks the first, from the address that routes to it, and the second only when the first has not answered within half a second); never the data, which goes directly between the two, nor that those two talk to each other. The relay learns nothing new (it may notice that a device's traffic moved off it).
- Anyone on the network path sees UDP traffic between the two addresses (DTLS 1.2), its sizes and timing, as it would see the WebSocket to the relay.
- While a device holds or seeks a direct link, the host has UDP sockets on ephemeral ports of each interface (16 links at most). A STUN request gets an answer only when it names that link's ICE username (exchanged inside the encrypted channel); aioice then checks its message integrity with the link's password and answers an error to one that names the username but fails it; a stranger's request gets no answer at all. Any other datagram is accepted only from the address ICE selected, as DTLS, and at most 4096 wait for the DTLS reader; the rest is dropped. Nothing listens before a device asks. Port mapping (on by default, "Open a port on the router" in Settings or `direct.portMapping`; never with "Same network only"): while a device connects and holds a direct link, the host asks its router, over PCP, NAT-PMP or UPnP IGD, to forward external UDP ports to that link's extra UDP sockets, one socket per port (the ports restrictive networks keep open for a service, `portmap.UDP_PORTS`, at most 12, the one the device last came in through first; else a socket's own, else any) while it connects, and once it has chosen its pair only the one it came in through stays, so that a device behind a symmetric NAT can reach it; with the remote desktop, the same for the agent's socket of a view, and, with the host's TLS TURN server, for its TCP port (443, else 8443). Each such port is open to the whole Internet but reaches only its ICE/DTLS socket, which answers a STUN request only when it names the link's ICE username and passes its integrity (secrets exchanged inside the encrypted channel), then DTLS with the device's certificate, as above: a stranger who scans the port gets no answer. It is asked for a short lease (one hour, renewed) and deleted when the link or the view ends, the setting is turned off and the host stops; a crash leaves it until its lease ends or the next start (`<state>/portmap.json`, 0600). Before a port is used, the host checks that the router really forwards it (a router may take a mapping and drop what comes): it maps that port for a moment (a 120 s lease, deleted at once) to a scratch socket that reads only a random 16-byte token, and sends the token to the router's public address from itself; nothing else is sent, and the verdict is kept six hours. Anyone on the local network who answers SSDP or PCP as the router could make this host believe a different address (the default gateway is the only one asked; UPnP is spoken only to URLs on its address, without redirects, and refuses XML with a DTD or entity); that costs a direct link, never content. The router learns nothing it does not already see; the logs name the protocol and ports, never an address; a host with a public address of its own or a gateway that is not private asks nobody.
- Downgrade: a relay or network attacker can block UDP and keep a device on the relay. That costs speed only: the content is protected the same way on both paths, and the ciphers are those of the jaunt channel either way.
- Switching path never replays anything to the application: each frame is accepted once, by its counter, whichever path brought it; frames sent on a direct link that fails are sent again over the relay and the duplicates dropped. Terminal input is delivered once or, if the whole channel breaks, not at all, as before.
- The host's ICE (aioice), DTLS (pyOpenSSL over OpenSSL) and SCTP (vendored from aiortc, pure Python) code is reachable only by a peer that completes ICE with the link's credentials; it has not been audited for this use. Turn direct links off per device (Settings, this device) or per host (Settings, the machine, "Direct connections").

Lending ports (docs/PROTOCOL.md "Lending ports"): a host lends the router ports it holds for its own direct links to the desktop app of the same computer, for that app's own links to other hosts, which reach it only through those ports on some networks. Only the local connection (the account's own processes) can ask. Datagrams that arrive on a lent port reach the app only after a STUN request that proves the password of the app's WebRTC connection; the host sends only to the app's own registered sockets on this computer and to addresses that proved it (at most four per lend, eight lends, ended with the connection, after an hour without a peer and after two minutes of silence per address), so a lent port is not an open relay. A stranger's datagram on a router port that names no link or lend gets no answer, as before. A process of the account could already send UDP anywhere; what it gains is a router port, which another of its own connections could have used.

Direct link over TLS (on with the direct link; docs/PROTOCOL.md "Direct link over TLS"): where UDP is blocked or only port 443 is open, a device may reach the host through a TURN server the host runs itself, over real TLS. The content is protected exactly as on any path (the jaunt channel inside, DTLS between the endpoints, fingerprints exchanged inside the encrypted channel): a TURN server, ours included, sees the same ciphertext a network observer would, and the relay is not involved in the data. What it exposes and why it is not a way in:
- **What listens.** One TCP port of the host (random, kept across restarts; the box's 443, else 8443, forwards to it once automatic port mapping is on) speaking TLS and then TURN. Nothing else is served on it; before the TLS handshake and before a valid long-term credential it answers only a challenge (401) and Binding. A connection that does not allocate within 15 s is closed, as is one with eight refused requests in a row (64 for authenticated permissions refused for a peer the server does not relay to: a browser asks one per candidate of the host); 64 connections and 48 allocations at most (12 per device). Connections are counted when accepted, before their TLS handshake: 16 handshakes at once (a new connection takes the place of the oldest one), 4 at once and 24 connections from one source address (an IPv6 /64), anything beyond closed at once, so that half-open connections from the Internet cannot take the host process's file descriptors (whose limit the host raises to its hard limit at start; its shells keep the one it started with). Its TURN code (host/jaunt/turn.py, standard library only) has not been audited.
- **Not an open relay.** Credentials are made only by this host, for the devices paired with it and, while they connect, for a guest's device and a public link's visitor (whose page needs them before its offer, so they come with the link's welcome, through the relay): username `<expiry>:<tag>` and an HMAC-SHA1 password keyed by a secret that exists only in the host process's memory, valid for one hour, given to the device inside its encrypted channel (never in a URL or a log). An allocation can reach only the host's own UDP sockets that serve that device (its direct link's ICE sockets, its remote desktop views' sockets): permissions and channels for any other address are refused, anything sent to another socket (even on the host's own address) is dropped, and nothing from any other socket is passed back. It cannot be used to reach other machines on the host's network, the host's loopback services or the Internet; a revoked device loses its allocations at once, and its credentials, as a visitor's once it is gone, make no new one. Guests' devices and visitors share 12 allocations (4 each), so that they never take those of the owner's devices. 16 MiB/s per allocation, no more than a megabyte queued for a slow device.
- **Certificate and key custody.** The private key is made on the host (`<state>/direct-tls/key.pem`, 0600) and never leaves it; the relay sees a certificate request (the public key) and returns the chain. Let's Encrypt issues the certificate for `*.<id>.direct.jauntusercontent.link` (`*.<id>.direct.jaunt.one` for a host released before names left jaunt.one, docs/PROTOCOL.md "Names outside jaunt.one") after the relay proves control of the name with a DNS record. The relay's Worker holds the ACME account key and a Cloudflare token that can edit DNS in the `jaunt.one` and `jauntusercontent.link` zones and nothing else (Worker secrets, docs/DEPLOYMENT.md): whoever controls the relay's Worker or those secrets can obtain certificates for any name in those zones and publish records there, which is more than the relay's routing role (it never holds a host's key or anyone's session keys), so they are as sensitive as the relay's deployment token. A certificate for the wildcard authenticates the TLS tunnel to the host's TURN server only; a person who obtained one would also need a host's address, a device's credentials and the DTLS fingerprints inside the encrypted channel to do anything with it.
- **Certificate Transparency and privacy.** Let's Encrypt logs every certificate publicly. The log shows `*.<id>.direct.jauntusercontent.link`, a random 100-bit id with no link to the room, the host's name or its IP address. The host's address is published in DNS only under a random 16-character label below that name (`<label>.<id>.direct.jauntusercontent.link`), rotated daily, which neither the certificate nor the logs reveal and which the relay hands to nobody but the host that asked; the host gives it to its paired devices and guests' devices, inside their encrypted channel, and to a public link's visitor that proved the link's key, in its welcome (which the relay carries in plaintext): each of them learns the host's public address from its candidates anyway. A device that knows it, or anyone who learns it, learns the host's public IP address and that something listens there; they can complete a TLS handshake and get a challenge, nothing more without credentials. The relay sees the host's public address already; it now also writes it into DNS, where a resolver sees it for the 3 hours a replaced label stays published and while the host is online, and the records remain until cleaned if the host never returns (random label, known to no one else). A certificate's existence tells that a host registered with this relay asked for one.
- **Who may ask the relay.** Only a registered host (a room with its host capability, so one admitted by a relay access key or a tester invite) calls `/v1/direct`; four new certificate orders per host per rolling week; the relay builds DNS names itself from its own id and label (a host cannot name a record); a request with an `Origin` is refused. With a Worker secret missing the relay issues nothing and says which one.
- Turn it off with the direct link setting (host) or "Same network only", which also stops the server; a device with the direct link off never asks for credentials.

jaunt's TURN server (stage 4, the last resort; docs/PROTOCOL.md "Direct link through jaunt's TURN server"): where no direct path connects, a device's direct link may go through a coturn server the project runs (`turn.jaunt.one`, on Oracle Cloud). The content is protected as on any path (the jaunt channel inside, DTLS between the device and the host, fingerprints exchanged inside the encrypted channel); what changes and what bounds it:
- **What the server sees.** The public addresses (and ports) of the device and of the host, when they talk and how much, and ciphertext. coturn logs its sessions (their addresses and usernames) on that server, kept three days; the relay keeps, per installation and per month (three months), how many bytes the server relayed for it, as its companion reads them from coturn's own usage lines (whole lines only, so text a stranger gets logged cannot pass for one) and never more per report than the server could have relayed in that interval. The username names the installation by an HMAC tag keyed by the server's secret, never the room, the host or the device.
- **Who gets credentials.** The relay makes them only for a registered host (its host token, so invitation-only like the relay), 30 asked an hour at most (90 of ten minutes) and 12 still valid per tester invite or relay key (whatever number of hosts it admitted), valid ten minutes for a device that renews them and one hour for a device released before that; the host gives them, inside the encrypted channel, only to a paired device (never a linked host, a guest, a public link's visitor or the local socket) whose own direct attempt just failed. Anyone holding them could relay through the server until they expire (ten minutes, or an hour for a device released before renewal existed) within the server's limits; a device whose link goes through the server asks for new credentials shortly before they end, and the relay checks the allowance again then; a credential is refused once that installation's usage plus a reserve for its credentials still out reaches its allowance (50 GB a month), but one already given keeps relaying until it expires, so an installation can go past its allowance by what its credentials relay in that time (coturn enforces no allowance itself, so this bound is the credentials' life); they are never in a URL or a log.
- **Not an open relay.** UDP relaying only, to public unicast addresses only (private, loopback, link-local, CGNAT, multicast and documentation ranges and the server's own network refused), 1 MB/s per session and direction, 24 allocations per credential, 1200 in all (one invite's or key's credentials: 288 at most).
- **What never goes through it.** Web pages (the host refuses a web stream on such a link, and so does the device) and the remote desktop (a view never gets the server, and the agent drops every datagram from its addresses): only the terminal and files.
- **Secret custody.** The secret coturn checks credentials with (`TURN_SECRET`) exists on that server (root only, and in coturn's configuration, readable by coturn) and as a Worker secret of the relay; whoever holds it can make credentials for any installation, report usage and ask the relay to publish `turn.jaunt.one` and to obtain its certificate, so it is as sensitive as the relay's deployment token. It is never in the repository.
- **Recovery of the machine.** The relay's Worker holds an Oracle API key (`OCI_CONFIG`) of a dedicated user whose policy reaches the compartment `jaunt-stage4` only: it can manage compute instances (and their boot volumes), use that compartment's subnets and vnics, and nothing else, there or anywhere; a quota policy caps that compartment at Always Free sizes. It starts, resets, deletes (only a running instance silent for four hours) or makes the one instance of that name, never anything beyond Always Free, never more than one, at most 8 attempts a day. Whoever holds that key (or the Worker) can do the same to that machine, which is a denial of the stage-4 service and not more (the content is protected end to end); they cannot reach the owner's other Oracle resources or the tenancy's identity. The key is a Worker secret, never in the repository.
- **The secret reaches a new machine through a single-use token**, not the metadata: the instance's metadata (readable by every process on it and by those who read the instance in Oracle's console) holds a random token the relay accepts once, for 45 minutes, over TLS, and trades for the secret; 20 wrong tokens an hour at most. Anyone who reads the metadata in that window could take the secret before the machine does (the machine then fails to enroll and is noticed); after it, the token is worth nothing.
- **Alerts** to the owner go through jaunt.one's Worker with the relay's admin key as bearer (plain text, 500 characters, the owner's chat only), carrying no address or secret.
- Turn it off with the direct link setting (host) or "Same network only"; deleting the Worker secret turns it off for everyone (hosts are refused credentials).

Remote desktop (off by default; preview; docs/DESKTOP.md): with the host setting on, a paired device can view, and with view and control access act on, the whole screen of the host account's graphical session: every window on it, notifications, a password manager or a document left open, whatever the person at that screen does meanwhile. The host's account can already read that screen; a paired device can already run commands as that account; the setting decides whether devices see it without asking. What protects it:
- Only paired devices (never a linked host, an AI session or the local socket), each with its access in Authorized devices (view and control, the default; view only; or no access; see Control below), and only while that device's encrypted channel runs over a direct link: a view opens only then and ends when the channel falls back to the relay, disconnects or the device is revoked (the device may then open a new view by itself once a direct link is back, under the same checks, docs/DESKTOP.md "Reconnecting"; the host keeps the resolution and the display of its size that the view asked for, and the agent running, 2 s, or two minutes once that device said over its channel that it reconnects the view, for that device's next offer only; a device gone silent still loses its view, and the mode, within 15 s); the video never goes through the relay, and the agent offers no relay candidate of its own (a device may reach the agent's sockets through the host's own TURN server over TLS, which relays to those sockets only, see Direct link over TLS). These rules are checked again after the agent started (a portal question may hold it) and before the answer goes back.
- The device's offer and the agent's answer, with each side's DTLS certificate fingerprint, travel inside the end-to-end encrypted channel, as for the direct link. The agent reports its certificate's fingerprint to the host over the private pipe it was started with, and the host refuses an answer naming any other: the relay can neither read nor replace either fingerprint, and each side's DTLS handshake fails unless the certificate presented matches the one signalled. The video is DTLS-SRTP (AES-GCM or AES-CM with HMAC-SHA1, as negotiated) from the agent to that device only; the screen is never written to disk, never sent to the relay, and the host relays no picture.
- The agent (`jaunt-desktop-agent`, Rust: str0m and its DTLS, Cisco's OpenH264 or the GPU's encoder through VA-API, the platform's capture) runs as the account, in its graphical session (X11: the display logind records for the account's session, else an X server socket the account owns, never another account's), only while a device views and for 30 s after, and exits with the host (its stdin closes); the host kills it when its output ends or it stops reading. While it runs it has a UDP socket on each interface address per view (8 views at most; 4 accepted by the host); a STUN request is answered only when it names the view's ICE username (exchanged in the encrypted channel) and passes its message integrity, and DTLS needs the device's certificate. Its ICE, DTLS, SRTP, RTP/RTCP and H.264 code is reachable by a peer that completes ICE with those credentials; it has not been audited for this use. Datagrams from anywhere reach its sockets, and their source address proves nothing: what is not STUN, DTLS or RTP/RTCP is dropped unread, what the WebRTC stack refuses is logged and dropped (never ending the view), a flood cannot take every turn from the video, a forged duplicate DTLS record during the handshake (which panics str0m's DTLS, dimpl 0.7.4) is filtered out, and a panic in that stack ends only that view. Its log is `<state>/desktop/agent.log` (0600, no picture).
- Asking the person at the screen: on Wayland the desktop portal shows its own dialog on the host's screen the first time, then hands out a restore token that the host keeps (`<state>/desktop/portal-token`, 0600, given to the next agent in its environment, never on its command line, never logged, never sent to a device; the latest one the portal handed out) so that later starts restore the same screen without asking, until the remote desktop is turned off in jaunt (which deletes the token); the portal's own record of the choice (its permission store) is of no use without the token; viewing without asking at this computer (off by default; only the person at the host turns it on, in the desktop app on that computer or `jaunt remote-desktop unattended on`, never a device; journaled; turned off with the remote desktop) skips that dialog entirely: on GNOME the agent opens Mutter's own remote desktop session, which Mutter grants any unsandboxed process of the session (only API versions known to jaunt, else the portal, which asks), on wlroots compositors (sway, Hyprland…) it reads the screens straight from the compositor with no portal at all, and a device may show any of them, and on KDE jaunt's own application id (`dev.jaunt.RemoteDesktop`, named by a hidden desktop file) is pre-authorized in the KDE portal's permission store, never the empty id of unnamed programs, and that desktop file asks KWin for its screen cast interface (`X-KDE-Wayland-Interfaces=zkde_screencast_unstable_v1`, which KWin grants to the program the file names, the agent) so that it can make a virtual output of a device's size; turning the setting off removes the file and the grant (read back from KWin and journaled), and an agent started while it is off removes a file left behind; the setting is then the consent, a consent signal rather than a boundary, since a paired device's shells could already capture this account's screen through the same APIs; the system's indicator still shows and its Stop counts as jaunt's Stop; a locked GNOME screen ends every view; on a Linux host with no screen, a desktop may be started for a view (off by default; only the person at the host turns it on, in the desktop app on that computer or `jaunt remote-desktop headless on`, never a device; journaled; only ever for the host's own account): nobody is at its screen, and gnome-shell outside GDM could never be unlocked, so its lock screen is off inside it (a dconf database of its own, locked; the account's own settings untouched), and jaunt's pairing and each device's access are what protect it, nothing typed on a device being taken as a password; it stops after the last view unless the owner keeps it running; GNOME and KDE show their screen sharing indicator while it runs; macOS asks for the Screen Recording permission once (TCC) and shows its recording indicator; on wlroots compositors asking still goes through the portal's question (xdg-desktop-portal-wlr's output chooser, where one is set up), which chooses the one screen a device may see, then the agent closes the portal's session and reads that screen itself through the compositor's screen copy protocols (ext-image-copy-capture or wlr-screencopy), which the compositor offers to any program of the session, as screenshot and VNC tools use them (jaunt adds no privilege), and nothing of the compositor's shows a view: a status bar that shows screen sharing from PipeWire streams (waybar's privacy module) shows none, there being no PipeWire stream; on X11 nothing asks and nothing shows by itself, and on Windows nothing asks while the capture border is drawn around the screen (Windows Graphics Capture): any program of the session can read the screen there. jaunt adds its own signs while a device views: on Linux a notification on the host's screen (the desktop's notification service) naming the devices, with Stop; in the jaunt desktop app running on the host, a banner naming them, with Stop; `jaunt remote-desktop stop` from the host's terminal. Stop ends every view at once and refuses new ones for a minute; turning the setting off ends them for good. Each view is journaled in `<state>/desktop/views.jsonl` (0600: device, start, end, why it ended; no picture), the latest shown in the host's settings and by `jaunt remote-desktop log`. A device cannot press Stop for the host (only the host's own clients can).
- The agent ships with the host release: each platform's binary is listed with its SHA-256 in the release manifest, and the installers and the updater check it before installing anything, then put it next to the runtime's Python, where the host looks for it (or `jaunt_DESKTOP_AGENT`, or `<state>/desktop/jaunt-desktop-agent`). Whoever can write any of these is the account itself. As for the wheel, the checksum detects a corrupted or substituted download, not a compromised publishing account. A released agent has no OpenH264 of its own (a build from source is not covered by Cisco's patent license): turning the setting on downloads Cisco's binary over HTTPS, checked against SHA-256 pins for the compressed file and the library, into `<state>/desktop/openh264` (0700). The agent pins the same SHA-256, accepts only an absolute path, and loads the very bytes it checked (Linux: a sealed memory file; elsewhere the file in a directory only the account can change), so a library swapped between check and load is not loaded. A released agent leaves out the test tools (`bench`, which writes the encoded screen to a file, `inject`, which types and clicks, `testpattern`, `clicks`, `sound-probe`: development and CI builds only) and refuses them before anything else. On macOS it runs as responsible for itself, so that Screen Recording and Accessibility are asked for the agent and not for the program that started it; the other side is that any program of the account that starts the agent (`serve`, with a WebRTC offer of its own over the agent's stdin) uses the permissions granted to it: a program macOS refused could, through it, see the screen and, with Accessibility granted, act on it. There jaunt adds a privilege to the account's other programs. Releases are not signed with a hardened runtime or an Apple identity, so macOS cannot tie the grant to a signature; grant those permissions on a Mac whose programs you trust, and remove them in System Settings when the remote desktop is not used.
- Sound (phase 3, docs/DESKTOP.md "Sound"): what the host's speakers play (every application's sound, notifications included) can go to a viewing device, never its microphone. Off by default per device: a device asks for it in its view's offer only when its person turned sound on (the choice is kept in that browser's local storage), and turns it on or off for its own view only (`desktop.sound`, any device that may view: sound is part of the view; never a linked host or the local socket). The agent captures the default output (Linux: its monitor, through PipeWire, else PulseAudio; macOS 13 and later: ScreenCaptureKit's system audio, under the Screen Recording permission the picture needs, the agent's own sound left out; Windows: WASAPI loopback) only while at least one viewing device has sound on, and stops 3 s after the last one turned it off; nothing is recorded or written to disk, and the captured sound leaves only as Opus inside that viewer's DTLS-SRTP media, over the direct link, like the picture. On Linux and Windows any program of the account's session can capture the output that way (jaunt adds no privilege), and nothing on the host's screen shows it; on macOS the system's recording indicator, already on for the picture, covers it. jaunt's own signs say who views, not whether they listen.
- Statistics (frame rate, bitrates, each viewer's bandwidth estimate and round trip) reach the devices that view, end to end encrypted like the rest.
- Control (phase 2, docs/DESKTOP.md "Control"): a device with view and control access (the default) can move the pointer, click, scroll, press keys and type in the host account's graphical session, which is what that account can do; set a device to view only, or to no access, to prevent it. Its input travels inside its end-to-end encrypted channel (never the media connection, never readable or forgeable by the relay) and the host checks every message on its own: a paired device (never a linked host, the local socket or an AI session), its access `control` at that moment, a view of its own connected at that moment, over a direct link, the setting on; each event is rebuilt from known fields with bounds (64 per message, 1,000 characters per text, no control characters but line breaks and tabs), and at most 300 events a second per device are taken. Input is never queued or replayed: what arrives for a view that is not connected is dropped, and a new channel means a new view, as does a reconnection after the view's path broke (the device sends nothing typed before or during the break to it). The agent releases the modifiers and buttons a view held when it ends (closed, channel dropped or off the direct link, device revoked or lowered to view only), when the device's page loses the focus, and when the agent stops, even on a panic; other keys are pressed and released at once. Typed text is not logged by the host or the agent (only counts of refused input). On X11 the agent binds characters the keyboard lacks to spare keycodes (unbound when it stops), which any program of the session sees as a keyboard map change; on Windows, Ctrl+Alt+Del, the secure desktop and elevated windows stay out of reach (Windows refuses them to a program of the session); on macOS input needs the Accessibility permission for `jaunt-desktop-agent`, which a person grants on the Mac (a device can only ask macOS to show its prompt there, at most every 10 s). The pointer's position goes back to every viewing device (it is part of the screen they see). The clipboard's text crosses between a device with view and control access and the host, end to end encrypted like input, only when that device asks (a paste in the view, the bar's menu) or while its view has the focus (a copy on the host then reaches it; the agent watches the host's clipboard only during that time and tells the host that it changed, never what); at most 256 KiB, never logged or written to disk by jaunt. A device with view and control access may also change the resolution of the screen shown, to one of its own modes, for the time of its view (the lowest asked for applies to every viewer); the screen's own mode comes back when no view asks any more, when the agent stops, and, if the agent dies, from a record the host keeps (0600) and applies at once and at its next start; a device that goes silent loses its view, and the mode, within 15 s. On X11 the agent owns the clipboard for what a device sent while it runs, so any program of the session can read that text, as it could after a paste at the keyboard. On GNOME and KDE the clipboard goes through the same remote desktop session as input (GNOME's portal question then also asks to allow clipboard access); characters the host's keyboard layout lacks are typed by pasting them through it, so they stay on the host's clipboard, and nothing is pressed after such a paste. On wlroots compositors the agent uses the virtual pointer and keyboard protocols and wlr-data-control, which the compositor offers to any program of the session (jaunt adds no privilege); its virtual keyboard's keymap names the characters typed (a program of the session can read a keymap). On GNOME and KDE input goes through the capture's own remote desktop session, which the host asks for a keyboard and a pointer when a paired device has view and control access: GNOME's portal question then asks to allow remote interaction, and viewing without asking (Mutter's own session) drives input too. A device keeps its touch mode (touchpad or direct) in the browser's local storage, unencrypted; nothing typed or seen is stored.
- Windows' virtual display driver (phase 6, docs/DESKTOP.md "Virtual display"; the public repository moukrea/jaunt-idd, MIT): a display sized to the viewing device needs jaunt's own indirect display driver, a user-mode driver (UMDF) that runs in Windows' driver host, which jaunt installs only through `jaunt remote-desktop driver install`, run by a person at that computer in a terminal: it says what changes and asks, then Windows asks for an administrator's approval (its own prompt, never answered for the person). jaunt installs only the release whose SHA-256 this version pins, also listed in that release's SHA256SUMS, checked again in a folder only administrators can write. A release signed by SignPath Foundation, the preferred way, is installed only when Windows accepts the catalog's and the DLL's signatures and SignPath Foundation made them, and Windows asks whether to install device software from "SignPath Foundation"; nothing is then signed on the computer. Until such a release exists, the pinned one is unsigned and is signed on the computer it is installed on, with a key used once: the consent says plainly that this computer will trust a certificate made for it, then the release's `install.ps1 -SignLocally`, as an administrator, makes "CN=jaunt indirect display driver (<computer name>)" (valid 2 years, RSA 3072, its key in the computer's store and not exportable; its only usage is code signing and it is not a certificate authority, both checked before use), adds its public part to the computer's Trusted Root Certification Authorities and Trusted Publishers, signs the package's catalog with it (the catalog holds the DLL's and the INF's hashes, so the DLL is not signed itself), and deletes its private key, checked gone, before installing: nothing else can ever be signed with it, there or elsewhere. It signs only a catalog nobody signed, never re-signs one, and undoes everything (key, certificate, staged copy, device) if a step fails. What it changes is that computer's trust in that one certificate, and only an administrator's approval allows it. It never installs a test-signed build or one whose catalog is unsigned, and never turns on test-signing mode. CI's Windows runner boots in test-signing mode, so it cannot show that a driver signed this way loads without it (docs/VALIDATION.md records what has been seen). The driver adds a monitor only when asked on its pipe, which admits SYSTEM and the installing account only and refuses remote clients; it removes a connection's monitors when that connection closes or stays silent for 5 s, and sends nothing over the network. `jaunt remote-desktop driver uninstall`, or Settings > Apps, removes its device, its driver package, its files, its entry and the certificate made for it, from every store.

Web servers (the Web panel; docs/PROTOCOL.md "Web channel"): a paired device can list the web servers this account runs on the host (port, page title, program, folder) and open TCP connections to them over its direct link. A paired device could already reach them through a shell (`curl localhost:8440`); this is a new path to them, protected so:
- Only paired devices, only over their own direct link: a stream is a data channel of that device's WebRTC connection, whose DTLS certificate fingerprint the device sent inside its end-to-end encrypted channel, so the relay can neither open one nor read one, and there is no relay fallback (the device refuses to open one without a direct link). A linked host, an AI session and the local socket open none; a revoked device loses its link, and its streams with it.
- Only to the account's own web servers: a listening TCP socket the account owns (Linux: its uid in `/proc/net/tcp`; macOS: `lsof` for the account; Windows: processes of the account's user), not one of the host's own, that answered HTTP or HTTPS. Never another account's server or a system service (a container port published by root's docker-proxy is root's), never another machine. What the device sends goes to that socket as it is.
- Finding them sends `GET /` naming `localhost` (and the same over TLS when the port said nothing) to each of the account's listening ports, and `GET /json/version` to a port whose root answered an error (to tell a debugger's port, which answers it, from an app), only while a device asks (its Web panel open), at most once a minute per port (five minutes for one that is not a web server) while the same process holds it: a program that acts on a bare GET of its root, or of `/json/version`, would see that. Nothing else is sent to a port, and the host logs none of it. The list reaches the account's paired devices only, end to end encrypted; titles, programs and folders say what the account works on.
- Bounds: 64 streams per device, 256 per host, 1 MiB in flight per stream and direction (a peer that sends more is cut off). On the host, a stream's messages wait while the encrypted channel has frames to send.

Web names (docs/PROTOCOL.md "Web names"): each host gets a public name, `<machine>.<user>.web.jauntusercontent.link`, and a Let's Encrypt certificate for it and its wildcard (a host that had `<machine>.<user>.jaunt.one` keeps it beside, with its own certificate, while one of its devices of an older version needs it, then only redirects it to the new one until that certificate ends: docs/PROTOCOL.md "Names outside jaunt.one"), which Certificate Transparency logs publish. That tells anyone that a host registered with this relay exists, its machine label (made from the name the owner gave the machine on a paired device, else from the host's own name: a name such as `emeric-laptop` says what it says; renaming the machine on a device changes it, and a certificate for the new name is then logged too, the old one staying in the logs) and a user label shared by the hosts of one person. The user label leads back to neither the invite, the relay key nor the room: it is an HMAC keyed by a secret derived from the relay's ACME account key, so whoever holds that key can tell which invite or key a label belongs to, as the relay's owner already can. No address is published under these names. The private key never leaves the host (`<state>/web-tls/key.pem`, 0600); the relay sees the certificate request only. Whoever controls the relay's Worker or its secrets can obtain certificates for any name in `jauntusercontent.link` or `jaunt.one`, as for direct links (above). The browser's TLS for these names will end in the host itself, a device passing its bytes along unread.

Web over HTTPS (docs/PROTOCOL.md "Web over HTTPS"): a browser of a paired computer opens the account's web servers on the host through the desktop app. What protects it:
- The browser's TLS ends in the host, with the host's own certificate and key (the key never leaves it). The host speaks HTTP/1.1 or, to a browser that offers it, HTTP/2 (hyper-h2, pure Python; docs/PROTOCOL.md): any program of the computer that reaches 127.0.0.1:4443 and completes TLS reaches that parser as well as the HTTP/1.1 one, with the same way in (the page that asks) in front of every request; h2's own limits apply (64 streams, 64 KiB of headers, flow-control windows, a connection that resets 200 streams in 10 s is sent away) and `jaunt_WEB_H2=0` turns it off. The desktop app passes the bytes along unread, and the relay never carries them (a direct link only).
- Every web name resolves to 127.0.0.1, for everyone (one DNS record): a browser always talks to its own computer, never to the host's address. A computer without the desktop app, or whose app does not have that host, answers nothing. A program that took 127.0.0.1:4443 before the app would get the browser's connection; without the host's key it cannot complete TLS for these names (the browser shows a certificate error), and learns only the name asked.
- Which names a device answers for is its own decision, not a host's: a host says its web name in its welcome, and a device takes it only when it has the relay's shape (`<machine>.<user>.web.jauntusercontent.link`, or `<machine>.<user>.jaunt.one`; a `.test` domain, which nothing public resolves, for tests) and no other machine holds that name or one above or below it; the owner's own machines come before a guest share's host. So no host, a stranger's included, can make a device's gate, browser proxy, Android VPN proxy or resolver take `github.com`, or another machine's name; the system setting's resolver rules cover only the zones of those names (`<user>.web.jauntusercontent.link`, `<user>.jaunt.one`). A device tells each host the domains its own gate takes (`web.device`), and a host keeps its old name only while a device says none of the new one: what a device says changes which of the host's own names it answers, never what another device takes.
- Any program of the computer can connect to 127.0.0.1:4443 and reach the host's HTTPS, but only a browser that the person let in from that device gets past the page that asks: the question in the app shows the address, the User-Agent the browser gives (its own claim) and a code that browser's page shows. Allow only a browser that just opened that address and shows that code. Each question belongs to the connection that asked it: its page sets a secret of its own (HttpOnly, for that address only), and only a request that carries it is told the answer and given the cookie, so another program that asks at the same moment with the same User-Agent gets a question and a code of its own, never the browser's. Another program, another account of the computer, a browser profile not let in, and the cookie of one device used through another are refused. Any program that reaches the gate can still make the device ask (4 questions waiting at once per device at most), which costs the person a question, not access.
- The cookie (`jaunt-web`, HttpOnly, Secure, SameSite=Lax, a year, for `<machine>.<user>.web.jauntusercontent.link` and the servers below it, never a wider domain; the old name's its own, for that name) is never passed to a server, the host keeps only its SHA-256, and Settings (Web panel, `web.browsers`) revokes it. The servers of one machine share that parent name, so one of them can set cookies the others receive, as servers on localhost do today. Every name under `jauntusercontent.link` is the same site for a browser (it is not a public suffix), and anyone can serve a page there: any registered host gets a valid certificate for its direct-link names, which resolve to its own address, and serves any site it likes as a public link (`<id>-c.jauntusercontent.link`). SameSite does not keep such a page from making the browser send its cookie with a request to this machine's servers. (Before 2026-10-28 these names were under `jaunt.one`, the same site as jaunt.one's own pages; they left it so that none of this reaches jaunt.one, which now serves only jaunt's site, relay and app; a host's old jaunt.one name, while kept, is the same site as jaunt.one's pages, as before.) So the host passes a request on only when it comes from one of this machine's own pages (the name asked and the names below it, by its Origin, else its Referer), when the browser made it by itself (an address typed, a bookmark), or when it is a GET or HEAD navigation (a link followed, from anywhere, as SameSite=Lax allows); a form posted, a fetch, an image or a WebSocket from any other page is refused before any server sees it. A browser that sends no fetch metadata (`Sec-Fetch-Site`) is judged on its Origin alone. Any cookie value the device let in admits a browser, so a cookie of the same name set from another name of the site does not lock it out. A page under jauntusercontent.link (another host's, a public link's) can still set cookies for the whole of jauntusercontent.link that this machine's servers then receive (cookie tossing, which defeats some CSRF tokens of a server's own), and can show the person a look-alike page with valid TLS.
- A server sees requests as from its own computer (Host `localhost:<port>`, Origin and Referer rewritten), so its own checks of those headers let them through: that is the point, and why only browsers let in get that far.
- On Android the app does the same on the phone (Chrome reaches it while the app runs; Android may stop an app in the background). Its own browser (the Web panel's In jaunt) is a separate WebView over the app, without the bridge the app's page has, that keeps to that machine's names and opens any other address outside; the phone lets it in itself, with a cookie the host makes for that device (`web.browser.token`), so no question is asked for it, and it is listed with the other browsers. It reaches the gate by a proxy of the app's own for those names only.
- Android's addresses without :4443 come with a VPN of jaunt's (`JauntVpn`), which Android asks the person about once, in its own dialog. It carries none of the phone's traffic: it routes nothing and blocks nothing (both address families stay allowed), and only sets a proxy for the hosts' web names, which sends a browser's connection for them to the app's 127.0.0.1 (the PAC file lists the names, which any program of the phone can read there; Certificate Transparency publishes them anyway). Every other address goes as it would without jaunt; jaunt's own app is left out of it. With another VPN on, jaunt does not start its own (Android allows one), and another VPN starting stops jaunt's. The proxy takes `CONNECT` to those names on port 443 only.
- A computer's addresses without :4443 (the desktop app's Settings, "Web addresses without :4443"; docs/PROTOCOL.md "Addresses without :4443 on a computer") change that computer, never a host, and only once the person chose it. The "browser proxy" (Windows, Linux) changes the account's own proxy setting while the app runs: the PAC file sends the hosts' web names to the app's gate and every other address `DIRECT`, so the app sees which of those names a browser opens, nothing else; any program of the computer can read that PAC file (the names, which Certificate Transparency publishes anyway); the gate takes `CONNECT` to those names on port 443 only, so it is not a proxy for anything else. jaunt never replaces an existing proxy setting (it refuses and says which), and puts its own back when it quits; a browser that ignores the system's proxy keeps :4443. The "system setting" (macOS, and on choice Windows, Linux) is made with the administrator's approval, which the system's own dialog asks for (jaunt never sees the password): a resolver rule for the person's zones only, an address of its own (`127.77.0.1`) and a redirect of that address's port 443 only, so no other program loses port 443; the app answers those names itself and asks no one. Any program of the computer can listen on `127.77.0.1` while the app does not (as on `127.0.0.1:4443`, above): it would get the browser's connection for those names but, without the host's key, cannot complete TLS. The files and rules it writes are listed in docs/TROUBLESHOOTING.md with how to remove them by hand; Off removes them, with the same approval, and uninstalling the app does not (turn it off first).
- Send to… (the Web panel): a paired device sends one of the account's web servers to another device of the host that opens them (the desktop and Android apps say so). That device alone gets a notification naming the sender, the server's title and its port; its Open opens the server there as its own Web panel would, a browser not yet let in still being asked about. Nothing else is sent: no address, no cookie, no secret. A paired device can thus show another device a notification with a server's title, as the host's other notifications show programs' words.
- Share… (the Web panel): the owner's device makes an invite for one web server and a time (an hour to no limit), for another jaunt user. Anyone who has the invite can pair with it once, as with a pairing code, until it is used, expires or is revoked: send it to that person only (a browser that opens it does not use it up: its page shows where the invite opens, and the Android app asks before pairing a link it was opened with; its code stays in the app, never in an address or a log). The guest's device reaches that server only (each stream and each HTTPS request is checked against the share, on the host): the share is bound to the program that served the port and its folder when it was made, so a server started later on the same port (another project, the same program from another folder) is refused to the guest and to a public link's visitors, its title included, and the owner's list shows the share paused until the server shared comes back (a share made before this check is bound to the first server it reaches); a program that runs from the same folder under the same name is taken for the same server. The guest's device gets none of the host's sessions, events or questions, holds no right of a paired device (at the relay, a client token of its share's own, never the room's, withdrawn when the share ends; see the routing tokens note below), and its browsers are let in by the guest. The guest's device keeps that it accepted a share (its invite says so), whatever that host's welcome says later: from that host it takes its browsers' questions only (no tabs, approvals, artifacts or notifications), keeps only its name, direct link and web name, enrolls it for no notification or browser push, and sends it none of its interface addresses. The guest sees the host's name, its web name, the server's title and the owner's device name. Revoking the share, or its end, forgets the guest's device at once. A share admits one guest, and guests are not counted among the host's paired devices (a host keeps at most 1000 of the owner's: a safety bound, not the control, which is the single-use pairing code), so a link that spreads cannot enroll more than one device per share or take the places of the owner's own devices; a guest device whose share is gone is removed by the host's periodic check. A server shared this way serves the guest whatever it serves the owner: share only what that person may use.
- Public links (the Web panel's Share…, docs/PROTOCOL.md "Public links"): anyone who has the link opens that one web server, without jaunt, until the link expires (an hour by default) or is revoked. The link's key is in its fragment: browsers never send it to a server; the relay sees the link's name (also in DNS queries and certificates' SNI), never the key, and the host checks it. The visitor's page comes from the relay (jaunt's banner, the connector and the service worker): whoever controls the relay could change that page, as for the app's page. The site runs on its own origin, in a frame the banner's page holds: it cannot remove or change the banner, nor navigate it. The site's bytes go from the host to the visitor's browser over WebRTC, DTLS-encrypted; the relay carries the signalling only, so a relay that lies could stand in the middle of a visitor's connection (no pairing secret authenticates a visitor): a public link is for what may be public. A visitor reaches that server only, as a guest does (the program and folder it was shared from, on its port), and nothing else of the host. Every visitor sees the account's user label (8 characters, also in its web names) and, as with any peer-to-peer connection, the host's public address and the one its traffic to the Internet leaves from (its LAN address, usually), with the name and credentials of the host's TURN server (Direct link over TLS); nothing else of the owner. A link's name stays with the host that first declared it, after it ends too: no other host can take over an address a link had (and with it what visitors' browsers keep for that origin). Visitors can report a link; five distinct reporters suspend it until the relay's owner looks, who can also block one (a block stays with the name, whoever declares it next): the share domain is separate from jaunt.one so that a registry acting on abuse never takes jaunt.one down (it would take hosts' web and direct-link names with it, which are under that domain too, never the site, the relay or the app). Agents make public links only as the owner chose (asked every time by default, or trusted, or never).
- The desktop app may pair with a relay without TLS only when that relay is on 127.0.0.1, as a page served from localhost may (the tests pair it with a local relay); any other relay needs `wss://`.

The primitives come from cryptography and Web Crypto. **Their composition into this protocol is new and has not received an external audit.** Tamper/replay and interoperability tests do not replace an audit. Do not describe jaunt as certified, invulnerable, or ready by default for sensitive production environments.

## What is not protected

- A compromised browser, machine, or system account remains compromised.
- GitHub Pages serves code that can access secrets after unlocking: an attacker controlling this repository, the private source repository or the page can replace the JavaScript. End-to-end encryption does not protect against a malicious client update.
- Without a password, keys are stored unencrypted in IndexedDB, like a remembered session. A password/PIN encrypts them at rest; a short PIN remains vulnerable to offline guessing. Prefer a long passphrase.
- The same vault keeps what the device last knew of each paired machine's tabs, so the sidebar lists an offline machine's tabs: their names as shown (a name a person gave, or the automatic name, which can be a folder or a title a program set), the program in them and their last activity. It is encrypted with the rest when the device is protected, goes with the machine when it is forgotten, and nothing of it is on the page while the device is locked. The sidebar's display choices (sort, grouping, and the room identifier of the one machine shown) are in the browser's local storage, unencrypted; the search is not kept.
- Locking stops connections and clears active views. It does not guarantee cryptographic erasure of browser RAM.
- Terminal replays, terminal output to clients that accept it, scrollback pages and download chunks are deflate-compressed before encryption, one independent stream per frame. The relay sees frame sizes; compression makes them depend on how repetitive the content is. Someone who can both inject text into a terminal or file and observe the relay's traffic could use that length side channel (CRIME-style) to test guesses about secrets shown next to it. Uploads, keyboard input and control messages are not compressed.
- The names users control under jaunt.one are one browser site (audit 2026-10, JA-10; accepted for now): every machine's web names (`<machine>.<user>.jaunt.one` and the servers below them) and the direct-link names are under jaunt.one, which is not on the Public Suffix List (not eligible for it yet), so a browser counts a page served under any of them, by any registered host, as the same site as all the others: SameSite cookies do not keep it from sending requests to another user's servers, it can set cookies for the whole of jaunt.one, and it can pass for another user's page with valid TLS. Shipped: each host's gate refuses cross-site requests to its servers (a form posted, a fetch, an image or a WebSocket from another site; "Web over HTTPS" above) and admits any cookie value its device let in, so a cookie set from another name does not lock its owner out. Planned: the names users control move to a domain of their own, jauntusercontent.link, apart from jaunt.one.
- A complete QR code grants shell access for ten minutes. Never put it in an issue, public screenshot, CI log, or analytics.
- Browser notifications are delivered through the browser's push service. Program-supplied notification titles and bodies are displayed and sent through that service; do not include secrets in notifications. Android follows system lock-screen privacy settings. Terminal output is not scraped for notifications.
- A device that asked (`notifications.wake`, the Android app's notification service) is given the notifications it missed while it was not connected: at most 20 for 6 hours, kept in the host's memory only (never written to disk, never sent to a service), forgotten on revoke, on `enabled: false` and when the host restarts. They go over the same encrypted channel as live ones, once the device is authenticated (docs/PROTOCOL.md, "Notifications while a device is away").
- Waking a closed Android app (opt-in by build and by relay: docs/PROTOCOL.md "Waking a closed app"): the relay sends Firebase Cloud Messaging a high-priority message `{wake: "1"}` for a device token a host was given by its own paired device, authenticated by the host token and bounded to 60 sends an hour per room. Google sees that token, the app's identity and when wakes happen; it never sees a title, a text, a session, a host name or a room, and no email or account of the owner is involved. The device token is asked for only when notifications are on, Firebase analytics are off, and a build without the project's values runs no Firebase code. A push is only a prompt: what the app shows comes over the authenticated, encrypted channel from the host.
- Relay access keys (Worker secret `RELAY_KEYS`, enforced by `RELAY_KEY_REQUIRED`) only decide which **new** hosts may register on the relay; they are not an authentication of hosts or devices, which remains the rooms' 256-bit capabilities and the end-to-end handshake. A key is a shared onboarding secret: anyone holding a valid one can register hosts on the owner's relay (and spend its quota) until the owner removes it; a room registered with a key of `RELAY_KEYS` stays registered after its removal (no per-room revocation for those). Rooms registered before enforcement are accepted by their capabilities alone. Hosts keep the key in `<state>/relay-key` (0600, outside `host.json`), send it only in the first WebSocket frame, never log it, and remove `jaunt_RELAY_KEY` from their environment so the daemon, its shells and their programs never inherit it. Pairing codes never contain it. The published configuration, installers and packages name no relay.
- Tester invites are per-person relay access keys that the relay creates and keeps as SHA-256 digests; a key is returned once, at creation, and never stored. They are managed through `POST /v1/admin/invites`, off unless the Worker secret `RELAY_ADMIN_KEY` is set, which it compares in constant time; the API accepts only POST with a bearer key, refuses requests carrying an `Origin`, has no CORS and logs nothing. Whoever holds `RELAY_ADMIN_KEY` can create keys that register hosts, list testers' names and the room ids their invites registered, and revoke or forget those registrations, block public links, and have the relay replace its TURN machine (`turn.replace`: delete the one instance and let the recovery make another from the configuration the relay was deployed with, within Always Free and the recovery's guards, at most one deletion an hour; a denial of the stage-4 service for some minutes, never more); it gives no access to any host or device (room capabilities and the end-to-end handshake are unchanged). A leaked invite key registers at most its host limit before the owner revokes it. Forgetting the rooms of a revoked invite deletes only registrations that record that invite, closing their connections (4004); anyone who then presents a valid key and knows such a room id could register it with their own capabilities, which denies service to the old host but reaches none of its devices, whose end-to-end handshake needs the host's pairing secrets. The owner's script never follows redirects (it would resend the admin key) and never puts a key in a URL. In GitHub Actions, whose logs and summaries are public on this repository, the workflow prints neither keys nor tester names: create and list are encrypted with age to `OWNER_PUBLIC_KEY` or refused before anything is created. Workflow inputs are run metadata, not secrets.
- Routing tokens (docs/PROTOCOL.md "Routing tokens"; what a client presents to the relay to be routed to its host, never a secret of the channel): with a relay that keeps them, every paired device, linked host and guest has a token of its own, registered by the host at the relay as a SHA-256 digest (the relay never holds a token) and withdrawn when the device is revoked or the share ends: the relay then closes its connections at once and refuses it. A pairing code carries a token made for it, which becomes the new device's own (the room's shared token is no longer in codes); someone who saw a code can hold a place at the relay with it for the ten minutes it lasts, and after its use as long as that device is not revoked. A device paired before gets its token inside the encrypted channel the first time it connects (nothing to do, nothing to scan again; one that is offline gets it at its next connection) and uses it from its next connection. The shared token stays valid while some device that can move has not, so that a client released before this keeps working; the host then withdraws it at the relay, but only when the relay's owner turned that on (Worker variable `ROUTE_WITHDRAW`, off by default) (a device not seen since routes began is waited for two weeks; a client that connected and never moved is not waited for). From then on a holder of the old shared token (a former guest, a revoked device, an old code) is admitted only to a small lane of the relay, four connections of thirty seconds and one per source, outside the sixteen places of the devices: it cannot take or push out a place of a device, but it can still learn, thirty seconds at a time, whether the host is online. In the lane the host's end-to-end handshake tells a device of the owner's its token or, for a client from before, to update. A token that leaks is withdrawn by revoking its device. The room's own host and client tokens registered at the relay still cannot be rotated by the owner. Beyond that the relay bounds what a holder of any token costs: sockets that have not authenticated are capped per source and the oldest of the most crowded source make way for a newcomer (the host reconnecting is never refused), and once 16 clients are connected a newcomer takes the place of one that the host never confirmed as having passed the end-to-end handshake (docs/PROTOCOL.md "Transport and identities"), so holding a token without a device secret does not keep the owner's devices out. A guest share's invite carries a token of that share's own; invites made before, or with a relay from before, carry the room's. Routing secrets are not a complete quota or anti-DDoS system.

## Shared GitHub Pages origin

Sites at `moukrea.github.io/another-project/` and `moukrea.github.io/jaunt/` share a browser origin. Another vulnerable project on that origin could target jaunt's storage. Paths are not a security boundary. For sensitive use, serve jaunt on a dedicated origin (its own domain/subdomain) and pair again there. A PIN protects keys at rest but does not replace origin isolation or trust in the JavaScript being served.

## Storage and permissions

`~/.local/share/jaunt/host.json` and the control socket are private to the current account. The directory uses mode 0700, state uses 0600, and writes are atomic. `attachments/` contains uploaded files; locking the app does not delete them. Remove unneeded attachments through the file browser.

On Windows the local control channel is a loopback TCP port instead of a 0600 Unix socket: any process of any account can connect to it, so every request must carry the random key in `%LOCALAPPDATA%\\jaunt\\control.json`, which only the account (and administrators) can read through the profile's ACL. The state directory relies on that ACL rather than POSIX modes.

Artifacts: a page Claude Code publishes from a jaunt shell is copied to `<state>/artifacts/` (0600) and sent to the account's paired devices. It is arbitrary HTML and JavaScript, so the clients never render it in jaunt's origin: it runs in `artifact.html` inside a sandboxed frame without `allow-same-origin` (an opaque origin with no access to jaunt's storage, keys, cookies or window), under that page's own policy: inline code and the cdnjs, jsDelivr, unpkg, Tailwind play CDN, jQuery and Google Fonts libraries claude.ai admits for artifacts (their scripts, style sheets, fonts, and `fetch` to those hosts), images and media from any https address (a GET that reveals the device's address, as an image already could), and `blob:` and `data:` URLs (bytes the frame already holds); no other script or connection. The frame may run forms (handled in script; `form-action 'none'`), lock the pointer after a click (the browser says how to get it back), ask for full screen, which never puts the frame itself in full screen (it is not allowed to): jaunt shows its artifact pane over the whole window, jaunt's own bar above the page, and the element the page named fills the frame, so nothing the page draws can cover jaunt's bar or pass for jaunt's unlock screen, and write the clipboard (`clipboard-write`; the legacy copy command already could on a click); it gets no `allow-modals` (an untrusted page's browser dialogs, `prompt()` included, would sit over jaunt and could ask for its passphrase): `alert`, `confirm` and `prompt` do nothing there. jaunt's own UI still loads no CDN script. The frame never reaches jaunt's own files: an address the page names in jaunt's origin (https, or `jaunt://app` in the desktop app) is answered inside the frame, from the page's own files or as a 404. The page's `localStorage` (which its opaque origin is refused) is a stand-in the frame keeps: the device stores it per artifact in an IndexedDB database of its own (`jaunt-artifact-storage`, apart from jaunt's keys and settings, at most 5 MiB per artifact and the last 200 artifacts), only what the page on screen sends; it is page data, as untrusted as the page. `sessionStorage` and cookies are kept in memory only. The claude.ai runtime jaunt provides to those pages (`claude.use`: db, user, artifact, downloads, permissions) is reached only by postMessage to the client, which binds every call to the artifact it shows: a page reads and writes its own documents and its own host copy, nothing else, and a file it offers is saved only through the device's normal save prompt. A page may also ask jaunt to select a terminal tab (`claude.use("terminal").open({host?, session})`, jaunt only): it can only select a tab that already exists on a host paired with this device, never create a shell, type, or resize, and it is never given the list of tabs, so it must already know the id (a service hands it over through the page's data); jaunt asks the person (Open or Cancel, naming the tab and the machine) unless the tab is the shell the artifact was published from, accepts one request at a time (the others are rejected), refuses a page the person declined until it is loaded again, and refuses while another dialog is open so a page can never dismiss a question. Files Claude Code uploads beside an artifact as assets (`Artifact` with `asset: true`; the page names them `/_blob/<id>`) are copied by the host from the local paths the tool reported, only for an artifact it already keeps, only regular files of media, font, PDF or text-data types that still match the uploaded SHA-256, into `<state>/artifacts/<id>.assets/` (0600, at most 64 MiB per artifact); the device fetches them over the encrypted channel and hands the bytes to the same sandboxed frame, which makes `blob:` URLs of them in its own opaque origin. They are as untrusted as the page and are removed with it. Supporting files a publish lists beside the page (`Artifact` `files`, a map or a list, sources under `root` or the session's working directory, as the tool takes them; a later publish adds or replaces what it lists, keeps the others and removes what it maps to null) are copied by the host when it records the publish, only regular files, at most 32 MiB each and 256 MiB and 511 files per artifact, into `<state>/artifacts/<id>.files/` (0600, named by SHA-256); a published path that would leave the artifact (`..`, absolute, backslashes) is refused. For a copy recorded before the host kept them, the host reads once the Claude Code conversation file that published it (`~/.claude/projects/*/<session>.jsonl`, only its `Artifact` calls and their results) and copies the files and assets those calls listed that are still on disk: a file only with the SHA-256 that publish recorded (`files_written`, when its result names it) and never through a symbolic link, and nothing for an artifact removed meanwhile. The desktop app grants an artifact frame neither full screen nor pointer lock (Electron shows no hint of how to leave them); it grants full screen to jaunt's own page only, for that pane. A device fetches a file only when the page on screen asks for it by its published path, and only one its host lists for that artifact; the frame never learns where the host keeps it. These files are as untrusted as the page and are removed with it. Its documents are page data, untrusted like the page: kept in `<state>/artifacts/<id>.db.json` (0600) and mirrored as `<stem>.jaunt-data.json` beside the page's source so the publishing Claude Code session can read them; pages should not store secrets there. Its hooks in `~/.claude/settings.json` are a PostToolUse entry for the `Artifact`, `ArtifactData` and `ArtifactComments` tools and the claude.ai Docs connector's tools (`mcp__claude_ai_Claude_Docs__*`, an anchored pattern) only and a UserPromptSubmit entry; they only talk to the local host, and turning "Show Claude Code artifacts" off removes them. What they add to the publishing session's context includes documents pages stored, labelled as page data from people, not instructions: a page's data is as untrusted as the page. A claude.ai artifact link Claude posts, live, in the rich view of the tab on screen opens the pane on jaunt's copy of that artifact when that shell published it (the same sandboxed frame); a click on an artifact link in the rich view or a terminal offers "Open in jaunt" or "Open on claude.ai" (a new tab, `noopener,noreferrer`); jaunt itself fetches nothing from claude.ai. A session can also publish a page to the host's library itself, with no claude.ai account (`jaunt_publish` and `jaunt publish`, docs/RICH_VIEW.md "jaunt publish"): the request travels the host's local control socket only (0600, the account that runs the host: no paired device, linked host or service can send it), names a local `.html`/`.md` file and the supporting files `files` lists, and is kept under exactly the limits, the 0600 copies and the sandboxed frame and policy above; it is as much (and as little) authority as the hook that records a Claude Code publish, and the page's code gains nothing by having been published this way. With `native` the host only returns the `Artifact` call the session may then make: it never calls claude.ai itself. Claude Docs (docs/RICH_VIEW.md, "Claude Docs"): a doc the session writes through the Docs connector lives behind its claude.ai account and the host, which holds no claude.ai credential, never fetches it. What jaunt keeps is what the session sent and got back: the hook hands the host each connector call's input and result (the guide and queries aside) and the Artifact call that created a doc from the Docs type; for a doc it did not hold, and when a rich view shows a conversation or a device asks for a link it has no copy of (`artifacts.lookup`, only the conversations of the rich views open on the host), the host reads the Claude Code conversation file (`~/.claude/projects/*/<session>.jsonl`, the path the hook names only when it is there and named so; only Docs connector calls, Artifact calls with a `type_url`, and their results; from where it last stopped, kept in `<state>/artifacts/docscan.json`). It keeps those calls in `<state>/artifacts/<id>.doclog.json` and the copy rebuilt from them in `<state>/artifacts/<id>.doc.json` (both 0600, removed with the entry): the doc's text, as the session saw it, is as private as the conversation, and reaches the account's paired devices end to end encrypted like every artifact. Its XML results are parsed with the standard library only after refusing any DTD or entity declaration. A device renders a doc in jaunt's own page, not in the artifact frame, because nothing in it is HTML or script: its Markdown goes through the rich view's renderer (elements from a fixed list and text nodes, HTML in the text shown as text, links only http, https and mailto, opened in a new tab without opener or referrer, no remote image loaded), and its dates, mentions, dropdown values, pending sections and chart rows are built as text. The copy may differ from the doc (people's edits since the session last read it, edits jaunt cannot reproduce); it says so when jaunt knows, and editing or commenting stays on claude.ai.

Automatic tab names (docs/WORKSPACE.md, "Tab names"): the host reads, for every shell and whatever any device shows, the window titles programs write in the terminal (OSC 0 and 2; never treated as notifications, and no other OSC payload, such as the clipboard's OSC 52, is ever exposed), the command line of the job in front of the shell (`/proc/<pid>/cmdline` on Linux, of its first process or, once that one exited, as in a pipeline, of another of its processes still running; `ps` elsewhere), of which only the first word without its folder is kept as the job's name (a program that rewrites its command line into a title, as npm does with `npm install <package>`, is named `npm`; never an argument), and the shell's current folder. For a shell running Claude Code it also reads, at most every 10 s and only while Claude Code's terminal title gives no name, its session registry record (`~/.claude/sessions/<pid>.json`, for a name given to the session) and the last 64 KiB of its transcript (only its `custom-title` and `ai-title` entries are kept); for Codex, the thread lock its process holds (Codex 0.160's managed daemon holds it instead: the rollout the process holds, else the newest rollout a Codex TUI opened in that shell's folder since it started, its first line read) and the newest `~/.codex/session_index.jsonl` row of that thread (at most every 10 s), or the thread name an attached app-server reports. The name that results (at most 120 characters, without control or bidirectional characters) and the folder are sent to the paired devices only, end to end encrypted like the session list, which a linked host does not get either (nor the sessions in its welcome); none of it is kept on the host's disk (an in-place update hands it over with the terminal's state; a name a person gives is kept in `sessions.json`, as before; a device keeps the names it last showed in its vault, see above). A title is shown as the program set it: a shell configured to put the command it runs in its title (some zsh and fish setups) puts that command line in the tab name, so it reaches the devices like the terminal output itself. Agents, the policy journal, notifications and the shell name an artifact records keep the session's own name, never a title a program set. Renders use text only.

A linked host (another of the owner's hosts, enrolled as a requester) gets only the replies to its own `agent.*` requests: none of what a host tells its paired devices and local clients (the messages between sessions and their text, pending approvals with their commands, artifacts, notifications, the workspace, update progress). What it may send is an allow-list too, refusing everything else: RPCs only, and of those the agent methods, each under the target's switches, its policy for that requester, its approvals and its journal (a requester blocked from typing is refused the list of shells, closed sessions and bridge sessions, and messages to them, too); never terminal input, a resize or any other message a paired device sends to its shells (docs/PROTOCOL.md "Host links").

Linking hosts (docs/AGENTS.md "Link"): a device links among themselves only the machines it paired as the owner's own (a pairing code the person accepted; never a guest share, whatever a machine says about itself). The code it asks a target for (`pair.issue`) makes a linked host and nothing else: the target takes the role from the code it issued, never from what the enrollee says, and binds the code to the room of the host it is for. A pairing link opened in a browser pairs only after the person confirms it (Pair, naming the machine), as the Android app asks for a link it is opened with. A link code asked on the host's local socket (the desktop app on that computer) is confirmed on a paired device first, like every code made there (below).

Approvals and rules (docs/AGENTS.md): the approval card, the allow-list rules and the journal see the whole command a requester runs (32 KiB at most) and the whole text it types (16 KiB at most), never a shortened prefix; the journal keeps a shortened copy with the length and SHA-256 of the whole. A rule pre-approves only a command of one line without control characters: anything else is asked.

Agents opening shells (`jaunt open` and the `jaunt_open` tool; right `open`, behind the switch "Typing into shells of this host"): a Claude Code or Codex session in one of this host's shells may ask to open a new shell of the owner's on the same machine, running one command line it gives (at most 2,000 characters, one line, no control characters), in a folder it names or its own. This starts a process with the owner's full rights, so it is never silent and never decided by the session: the owner is asked on a paired device only, with the requester, the command, the folder and the tab's name (the session sits on the host's local socket, where it could otherwise answer for itself, so neither the CLI nor the desktop app on the same computer answers it, and trusting the right is refused from there too; lowering it or blocking works from anywhere). "Allow until restart" lets that requester (every Claude Code, or every Codex, session of this machine) open shells until the host restarts, its level is changed or it is revoked; a trust of 1 h or always does the same without asking. Every shell opened is a tab in every client, with a notice naming who opened it, a notification (urgent, like an approval), and a journal row with the command, the folder, the decision and what happened; at most 5 a minute per requester. The shell is the owner's like any other (it lives until the owner closes it, it is not an agent shell with a lease, and the session gets no right to type into it or read it from opening it). The command is typed at the new shell's prompt, as the owner would type it, so it runs with the shell's own startup files; it can do anything the owner can, which is why the question shows it whole: allow it only for a session you trust with that.

Agents sending web servers (`jaunt web` and the `jaunt_web` tool; right `web`, while Agents and machines is on): a Claude Code or Codex session in a jaunt shell lists the account's web servers (what any program of the account could find) and the devices that open them, and may send one server to one of those devices. The first send is asked on a paired device (never from the local socket, where the session itself sits); allowing holds until the host restarts, and trusting it longer is likewise for a paired device only. The device shows each send as a notification naming the session; opening it lets nothing in that a browser of that device would not be asked about. Every send is journaled; Block in Settings stops them.

Browser controlled by AI sessions (docs/BROWSER.md; off by default, the host switch of that name; the `jaunt_browser_*` tools, right `browser`): a Claude Code, Codex or OpenCode session in one of this host's shells drives a Chromium the host starts with profiles of its own (`<state>/browser/profiles/`, 0700, kept between starts: the sites signed in there stay signed in), never the owner's own browser or profile. The host drives it only through `--remote-debugging-pipe` (two pipes it holds, no port: no other program of the machine, of this account or another, reaches the browser); Chromium is Google's Chrome for Testing of one pinned version, downloaded over HTTPS when the switch is used, checked against its pinned SHA-256 and size, unpacked into `<state>/browser/chromium/` (0700) with every file and link kept inside it, and run only once a marker written last says so. What a session may do is decided by the host, never the session: its right (ask: the owner's first allow covers that session only, its shell and conversation, JA-15; trust 1 h, 24 h or always covers that runtime's sessions; block), each site the first time it acts there (once, this session, or always for that site; a bank, payment, broker or tax site is never "always"), and each script (`javascript`, shown whole, once or for that site in this session, never for good: a script reads what the page's scripts read, some cookies included). Answers come from a paired device, the desktop app or a terminal outside jaunt; from a jaunt shell the host refuses answering, trusting and letting a stopped session back in (JA-14). Hard-coded and not configurable: no tool acts on or reads jaunt's own pages (jaunt.one and its subdomains, the published app, this host's relay and page, where a session could approve its own requests), the browser's own pages and other non-web schemes (`chrome:`, `chrome-extension:`, `devtools:`, `file:`, `data:`, …), extension stores or password managers; no tool reads cookies or saved passwords, and a password field's value is never read. Each driven tab shows a banner (who drives it, Stop) built with `textContent` in a closed shadow root from an isolated world of jaunt's own, whose Stop calls a binding the page's scripts cannot reach; every device shows a live card with Stop. Stopping detaches from that session's tabs, withdraws its grants and the question it waits on, and refuses its calls until the owner lets it back in. Page content returned to a session is wrapped as coming from the web, never from the user; that is a label, not a defence against prompt injection: the defence is the approval per site and the session's right, and a session that also has a shell should be trusted as one that can act as the account. Every action is journaled (session, tool, site, address without query or fragment, decision), never what was typed, read or run; screenshots are kept in `<state>/browser/screenshots/` (0600, the 20 newest) and Chromium's own messages in `<state>/browser/logs/` (0600). A linked host and a guest get nothing of it.

AI sessions and the local socket (audit 2026-10, JA-14 and JA-15): every program of the account reaches the host's local control socket, an AI session in a jaunt shell and the commands it starts included. The host looks at the process at the other end of each connection (Linux: its pid from the socket, then the systemd scope the host starts each shell in, its ancestry and its terminal; macOS: its pid from the socket, its ancestry and its terminal; Windows: the pid jaunt's command line declares, then its ancestry; what Codex's shared background server runs counts as in a jaunt shell too) and refuses to a program running in one of its jaunt shells what only a person decides: answering a session's permission, question or plan (`rich.answer`, and keys that would answer a dialog or a question card), answering an approval card, trusting a requester, adding an allow-list rule. Those come from a paired device, or from the desktop app or a terminal of the computer outside jaunt. Lowering a right or blocking a requester works from anywhere, and the session's ordinary work goes on: typing into its own shell, jaunt's tools under the rights below. From a jaunt shell, `jaunt remote-desktop stop`, `unattended` and `headless` and the virtual display driver's install or removal (whose consent was any terminal answering y; Windows then still asks for an administrator's approval) are confirmed on a paired device first, and refused while none is paired.

Pairing from the computer itself: a pairing code asked on the local socket (`jaunt pair`, the desktop app's Pair device, a link code the desktop app asks its own host for) is made only once one of the owner's paired devices confirms it, whoever asks, an AI session included; the program asking cannot answer that question, and the code does not exist before. While no device is paired, the person at the computer is the confirmation (the first device needs nothing else), and a code made then is refused once a device has been paired. Every enrollment, of a device, a linked host or a guest, is notified to every device (urgent) and journaled with who had its code made.

Shell grants (right `type`, docs/AGENTS.md): "Allow for this shell" lets the session that asked, that is its jaunt shell and the conversation its runtime holds there, type into and read that shell; another Claude Code or Codex session of the machine, or a new conversation in the same tab, is asked again (a linked host names its own sessions; one from before that names none keeps the former grant for all its sessions). Trusting a requester (1 h, 24 h, always) covers all its sessions, as the card says, and "Allow until restart" of the rights `open` and `web` holds for the requester, as above. Claude Code's settings pre-approve the tools of jaunt's MCP server (fifteen, and the twelve of the browser) while the bridge or Agents and machines is on (docs/BRIDGE.md), so Claude Code itself does not ask before a session uses them: what they may do is decided on the host, by its switches, each requester's rights, the approvals and these grants.

What this does not do: it tells an AI session's ordinary means apart from the person's, and is no boundary against the account itself. A program running as the account can leave what the host looks at (the processes, terminal and scope of a jaunt shell), or change jaunt's own files and state; on hosts without systemd scopes (macOS, Linux without a user service manager), a program a jaunt shell starts inside tmux or detached from its terminal is not recognised as the shell's; on Windows, neither is a program that talks to the loopback port without jaunt's command line. Hence the confirmation of every pairing code made at the computer, whoever asks: an AI session that may run any command should be trusted as one that can act as the account.

Closing and the background (docs/WORKSPACE.md): closing a tab ends its shells for every device (a tmux session is only detached), after a question when something runs there; the background is a flag every paired device can set or clear (`session.background`), never a linked host. Watching a shell is read only on the device (no input path, no size claimed) and attaches its stream like any view. A device can watch the agent shells requesters keep on its host: `agents.shell.peek` reads an agent shell's log for paired devices only (refused to linked hosts, like every non-`agent.*` method) and never renews its lease, and the list of agent shells (requester, folder, times) is sent to paired devices, never to linked hosts.

Renaming a tab that runs Claude Code or Codex (docs/WORKSPACE.md): only on a paired device's `session.rename` with a name (never from a linked host or an AI session, never on "Automatic name"), the host gives that program the name typed, made one line in which each run of control or format characters (Unicode Cc and Cf, zero-width and bidirectional ones included) and of line or paragraph separators is one space, as Claude Code itself does, at most 80 characters, and nothing else. For Claude Code it writes one control frame, `{"type": "control", "action": "rename", "name", "session_id"}`, to the inbox of the Claude Code process in front of that shell (the socket its registry record names, after the peer token published beside it, as for bridge deliveries; a frame for another conversation is ignored by Claude Code), then reads its registry record back for the name it took; it never appends to its transcript or registry itself. Only when that session has no inbox or its inbox does not answer, and on Windows hosts always (jaunt reaches the inbox as a unix socket only), and then only while the rich view is on and Claude Code is idle at an empty prompt, it types `/rename <name>` there instead, under the rich view's rules for typing. For Codex it sends `thread/name/set` to the app-server jaunt's launcher attached; a Codex not started that way gets nothing. The program then records the name as for its own rename (Claude Code: its registry, `custom-title` and `agent-name` transcript entries, a `custom-title.json` beside the transcript; Codex: `session_index.jsonl`), where it also serves to address or resume that session (Claude Code's peer name, `codex resume <name>`).

Rich view (off by default; "Rich view for Claude Code and Codex"): while a device shows a tab running Claude Code or Codex as a conversation, the host reads, and never writes, that runtime's own files: Claude Code's session registry (`~/.claude/sessions/<pid>.json`), the conversation transcript (`~/.claude/projects/…/<id>.jsonl`), a plan file under `~/.claude/plans/` that a plan names when it carries no text of its own, the files of the conversation's agents and teammates beside the transcript (`<id>/subagents/agent-<id>.jsonl` and `.meta.json`, read only while a device has the session open; an agent's conversation is sent to the devices that open that agent, as the main conversation is, to the same peers and under the same rights), the files of the conversation's workflow runs (`<id>/subagents/workflows/wf_<id>/journal.jsonl` and the agents' transcripts beside it, `<id>/workflows/wf_<id>.json` and `<id>/workflows/scripts/*.js`: a run's agents, journal, result, log and script, read only while a device has the session open and sent, like the conversation, to the devices that open the run, under the same rights); the terminal's `/workflows` screen, which the host already reads while a device looks, only for the words "paused" and "stopped" next to a run (nothing else of that screen is kept), and `~/.claude.json` for the usage it caches (only `cachedUsageUtilization` is kept); for Codex the thread lock held by the shell's process (with Codex 0.160's managed daemon, which holds the locks: the thread that daemon lists with an MCP server on a loopback port the shell's codex process itself listens on, else the rollout that process holds, else the first line of the rollouts opened in the shell's folder since that Codex started, to find its own), the rollout (`~/.codex/sessions/…/rollout-*.jsonl`) and `~/.codex/session_index.jsonl` for the thread's name. It sends that conversation (messages, reasoning summaries, tool inputs and outputs, diffs) to the devices that open the view, end to end encrypted like terminal output. Nothing of it is written to disk by jaunt: the host keeps the last items of open views in memory, and devices cache none of it (their local storage keeps only which view each tab shows and the person's own unsent draft in each tab's message box, until it is sent or emptied; both are removed when the machine is forgotten). For Claude Code, the view can also act, only through Claude Code's own mechanisms and only from a paired device (never a linked host or an AI session; a service such as AgentsWorld only under its own `answer` right, below): (1) while the setting is on, a `PermissionRequest` hook group in Claude Code's user settings (no matcher, `…/hook-claude rich`, removed when the setting is turned off; the person's own groups are never touched) sends each permission, question and plan to the host over the local control socket, which no peer can reach; the hook outputs a decision only when a person answered on a device, and nothing otherwise (Claude Code then asks in its terminal as usual; outside a jaunt shell, for another process or conversation, or with the host down, it returns at once). "Allow for this session" rewrites every suggested permission to `destination: "session"`, so nothing is saved to user, project or local settings, and the card says what it allows (a switch to accepting every edit included). (2) Messages, Stop and `/model`/`/effort` are keys typed into the shell's terminal, exactly as a keyboard would: the host types only when its own copy of the screen shows Claude Code's empty prompt (the live, bottom-most box, with the cursor in it) and its registry is not waiting for an answer, one action at a time per shell, and presses Enter after a paste only when, right before it, the same Claude Code still has the foreground and its prompt shows the pasted text: never into a dialog (whose option 1 an Enter would pick) and never into the shell after `claude` exited. An action is executed at most once per operation id and never replayed after a reconnection. A message the session cannot take yet (a prompt or dialog open, a draft in its prompt, not registered yet) is held by the host in memory, per shell, until it can be typed under those same rules, or a device cancels it; held messages (their text, and their uploaded images, which stay in `<state>/rich/images/` meanwhile) are handed over to the new runtime in an update inside the same private unlinked snapshot as the terminals, and never written elsewhere. A message typed whose Enter had to wait is never typed again: the host presses Enter only once the prompt shows exactly that text with nothing asked. A `/model` or `/effort` typed this way is saved by Claude Code as the person's default, which the view says; they are typed only while Claude Code is idle (held until then). An option of a picker the runtime shows (its `/model`, its `/effort` scale) is chosen by the host as a person would, one arrow at a time, each checked on its copy of the screen, and Enter (or the picker's own session-only key) is pressed only when that same picker shows that option highlighted. While the setting is on, the `statusLine` of Claude Code's user settings runs jaunt's wrapper `<state>/rich/jaunt-statusline`, a POSIX sh script (no interpreter, no network, no host call) that chains the person's own status line command, if any, with the same stdin, output and exit status; only `command` is replaced, the person's original object is kept in `<state>/rich/statusline.json` (0600) and on a comment line of the wrapper, and turning the setting off (or `jaunt service uninstall`) puts it back exactly; a status line the person sets meanwhile is adopted as the one to chain, never overwritten or wrapped twice. In a jaunt shell (a session id of `A-Z a-z 0-9 _ -` only) the wrapper also writes the status line JSON Claude Code sent to `<state>/rich/statusline/<jaunt session>.json` (0700 directory created by the host, 0600 file, temporary file then `mv`; nothing when the directory is absent). That JSON holds session metadata, not the conversation: session and prompt ids, the transcript, working and scratchpad paths, the conversation's title, model, effort, context and token counts, cost, prompt cache statistics, the account's rate limits, versions; no message, tool input or output. The host reads the file of the shell a device shows and sends the limits, effort, context window, cost and cache state to that device like the rest of the view; the file is overwritten at each refresh, removed within a minute of its shell ending, and all of them when the setting is turned off. Jaunt shells never inherit the Claude Code or Codex session identity of whoever started the host (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_PID`, `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_EXECPATH`, `CODEX_THREAD_ID`, `CODEX_SESSION_ID`); configuration such as `CLAUDE_CONFIG_DIR` and `CODEX_HOME` is kept. For Codex (Linux hosts only), jaunt shells have `<state>/rich/bin` first on their `PATH` (a bash shell puts it back in front after the person's `~/.bashrc`, through the host's `<state>/rich/shell/bashrc`, which only reads that file and moves that one folder); on a machine that has a `codex`, it holds jaunt's `codex` launcher script (elsewhere it is empty, so nothing named `codex` appears), which runs the real `codex` with the arguments unchanged unless the setting is on (the flag file `<state>/rich/codex-on`), the shell is a jaunt shell, the command is the interactive TUI and the interpreter it names still exists. Then it runs jaunt's launcher with Python in isolated mode (`-I`): the shell's current directory and its `PYTHONPATH`/`PYTHONHOME` never reach the interpreter, so typing `codex` in a repository never runs that repository's `.py` files (the bridge's hook and MCP wrappers run the same way). The launcher asks the host first, over the local control socket, whether it is the foreground job of the jaunt shell it names (a tmux pane, a program started from a jaunt shell, or a host that is not running gets the real `codex` as it is), then starts Codex's own `app-server` on a unix socket in a private directory (`$XDG_RUNTIME_DIR/jaunt-codex` or `/tmp/jaunt-codex-<uid>`, 0700, checked to be a real directory owned by the account; one socket per launch, never a TCP listener), with the shell's environment and directory, and runs the same TUI against it (`--remote`, no other argument). A detached watchdog, started with the app-server, stops it once the TUI exits or the launcher dies: it first interrupts any turn still running (so closing the tab or killing Codex stops the agent's tools as quickly as it would without jaunt), then SIGTERM, then SIGKILL after 10 s. The host accepts the launcher's notice only over the local control socket, from a process of that shell's foreground job, for such a private socket (Codex 0.160 makes the socket a symlink to a socket of that app-server's own in `/tmp/codex-daemon-<uid>`: the link and what it resolves to must both be the account's, in directories no one else can use or replace, and the host checks the listening process's user through each connection it opens, sending nothing to one that fails); a notice it refuses makes the launcher stop its app-server and run Codex as it is. It keeps only metadata of an attach (`<state>/rich/codex-attached.json`: session, socket, pids and their start times, the id of the thread on screen) and connects to it as a second client. It answers Codex's approvals and questions only with what a person chose on a device (first answer wins with the terminal), shows what an approval also grants (a command's additional network and file-system permissions, a file change's session-wide write root) and offers only refusals for a request carrying a permission it cannot show, never offers the decision that saves a permanent rule (`~/.codex/rules`), and passes a secret answer (`isSecret`) to Codex without logging or keeping it; a message or Stop from a device is `turn/start`, `turn/steer` or `turn/interrupt`, executed once per operation id. The model and effort change either the running thread only or, as the view says, the running thread and Codex's defaults in its `config.toml` (as Codex's own picker does on Enter); `/model …` and `/effort …` written in the view are applied the same way and never typed into its TUI, which would hand them to the model as a message. The app-server's own output goes to `<state>/rich/codex-<pid>.log` (0600). The launcher leaves only `--no-daemon` out of the TUI's arguments (Codex refuses it next to `--remote`; the launcher's app-server already serves that TUI alone). A plain Codex under Codex 0.157+'s shared background server (its managed daemon: one app-server per `CODEX_HOME`, started by the first TUI that needs it with that TUI's environment, running every terminal's threads, hooks and MCP servers) is attached the same way, with no notice, only when the shell's own foreground codex process listens on the loopback port that the daemon lists as an MCP server of a thread (the TUI's own server): the host then connects to the daemon's socket (`$CODEX_HOME/app-server-control/app-server-control.sock`, resolved, link and target checked private as above, the listening process this user's), follows and acts on that TUI's threads only, and never stops, restarts or reconfigures the daemon nor interrupts anything when the TUI exits. No process is counted as a jaunt shell's through a managed daemon: the bridge counts a hook the daemon runs for the shell whose codex TUI holds that hook's thread by that same port rule (or refuses it), and an MCP tool call by the thread Codex names in it. Other Codex sessions are driven only through their terminal, as a person at it would. A Codex session's sub-agents (Codex 0.160's multi-agent v2: threads of the same app-server) are shown from the same files, the rollouts of the threads the session's own conversation names (`sessions/…/rollout-*-<thread id>.jsonl`, found by the thread's id and read only while a device shows the view), and, for an attached session, from the connection: the host subscribes to those sub-agent threads (read-only: `thread/resume` without turns) to hear their status, the command one runs now and the approvals and questions one asks, which a device may answer with the same call and the same first-answer-wins rule as the main conversation's. The only action on a sub-agent is `turn/interrupt` of its running turn, from a paired device's Stop or Stop all (never from a linked host or an AI session; for an attached session only); writing to one is refused by the host, as Codex refuses it to any client but the agent that owns the sub-agent. Nothing is written to Codex's files. Images a person adds to a message in the rich view are this person's data: the device keeps an unsent draft's images in its IndexedDB (removed with the draft, and when the machine is forgotten); on Send they are uploaded through the transfer path into `<state>/rich/images/` (0700, files 0600, named after the transfer), checked (that directory only, a regular file, size, PNG/JPEG/GIF/WebP by content, the device's SHA-256) and removed once the send is over, whatever its outcome (a Codex turn's once it ends, or the attach ends; anything left after an hour, or at host start). For Claude Code the host pastes each image file's absolute path, as a person dropping the file on that terminal would: Claude Code reads the file itself (a hard link of the upload, else a copy, in `<state>/rich/images/pasted/`, 0700, files 0600, removed once Claude Code showed the image, else with the hourly sweep); no desktop clipboard is used, so the person's own clipboard is never overwritten. The terminal's image paste into a tab running Claude Code pastes the uploaded attachment's path the same way. The images a conversation already holds are read from the runtime's files on request (`rich.image`) and sent to the device end to end encrypted, kept in the host's memory only while fetched; neither side logs an image or writes one elsewhere.

To reopen shells after a restart, the host keeps `sessions.json` (each shell's name and whether a person gave it, directory, size, whether it is in the background, when something was last typed into it or came out of it, and the id of the Claude Code or Codex conversation it ran) and, while terminal history on disk is on, `scrollback/<id>/screen.json.z` (its history lines and screen as text) next to the raw history, all 0600. Everything a shell printed can therefore stay on disk until the shell is closed; turn off "Keep terminal history on disk" to keep only names and directories, or "Reopen shells after a restart" to keep nothing. A reopened shell runs nothing else by itself: a conversation's resume command (its id and the options the program ran with, never a prompt) is typed at the prompt and run, unless someone typed into the shell first. A shell opened with Claude Code or Codex from the top bar (`session.create` `launch`) is the exception a device asks for: the host types `claude <arguments>` or `codex <arguments>` and Enter at its new prompt, which gives a paired device no right it lacked (it can type anything in its shells). The arguments are one line with no control or bidirectional character. The request itself is never stored nor typed again (not in `sessions.json`, not handed over in an update), but the typed line `claude <arguments>` is terminal output like anything typed: it is in that shell's history kept by the host (on disk while "Keep terminal history on disk" is on, and handed over in an update) and in the shell's own command history, so a secret does not belong in the arguments (use the program's own configuration or environment instead). Arguments kept as a device's default stay in that device's vault (encrypted when the device is protected), never in the browser's local storage. On Linux the installer enables systemd lingering (`loginctl enable-linger`; set `jaunt_NO_LINGER=1` to skip it), so the host and its shells run from boot without a login session.

Shells outlive the host process through the PTY holder (Linux and macOS, docs/PROTOCOL.md "Restart survival"): a separate process of the same account, started by the host, that keeps a duplicate of each shell's PTY master (and, on Linux, a pidfd of the shell) while no host runs. It reads and writes no terminal and keeps none of their output; in memory it holds each shell's name, folder, size, program name and creation time, and writes nothing but `<state>/ptyhold.log` (start, exit, shells ended or released, with their ids and pids, 256 KiB at most) and its lock file. Its socket, `<state>/ptyhold.sock`, has the control socket's access model: 0600 in the 0700 state directory, and it also refuses a peer of another uid (`SO_PEERCRED`, `LOCAL_PEERCRED` on macOS). Whoever can use that socket is the account itself, which can already read and write its own terminals: it could take a copy of a held PTY and type into it, as it could through the control socket. Requests are bounded and validated (identifiers, a terminal and the pidfd of the stated pid for `put`, sizes); nothing in them is run or opened. A shell left in the holder keeps running with nobody reading it until a host comes back, `jaunt stop` ends it, or the machine restarts. Under systemd each shell runs in a transient user scope named `jaunt-shell-<session id>-<random>`, created through the account's own service manager: the session ids (already in each shell's environment) are visible to that account and to root in `systemctl --user` and the control group paths.

Feedback (the sidebar's Feedback button; docs/PROTOCOL.md "Feedback"): the only thing that leaves a host for jaunt's maintainer, and only when a person clicks Send in the dialog. The device asks its host (`feedback.send`, paired devices only), and the host makes one HTTPS POST to `jaunt.one/api/feedback` with its relay access key in the Authorization header (never in a URL, never logged, never in the body). What is sent is what the dialog showed: the type, the message, a fixed set of technical details shown verbatim (jaunt versions of the host and the app, the operating systems, the kind of app, the kind of view such as a terminal or a Claude Code conversation; no paths, session content, shell output or machine names), and up to four pictures only if the person added them (chose, pasted or dropped images, or ticked the option for a screenshot of the app's window) and saw each one in the dialog first; a picture may show whatever it shows, terminal text included. The app draws each picture again into a JPEG on the device (so what leaves is pixels, never the original file, an SVG or a page), the host keeps each in memory for ten minutes at most, never on disk, and checks its type and its first and last bytes, and the Worker checks them again; the maintainer sees them in Telegram as photos or files and saves them with the script. jaunt.one learns the sender's IP address (as any site does) and, from the relay, which tester invite the key belongs to (the label the owner gave it), so the maintainer can tell who wrote; it stores the feedback and posts it to the maintainer's Telegram chat as plain text, where the maintainer's replies are kept as notes with it. Telegram and Cloudflare therefore see it. Each host sends at most ten an hour and one every 15 seconds, and the Worker caps per key and in all; a key the relay does not know or has revoked is refused. The relay's `resolve` admin action is read only and takes a digest; a host with no key of its own proves itself with its room id and the SHA-256 of its host token (which the room already stores, and which cannot be used to connect), so it is identified as "registered host" and its invite's label if a live invite registered it. The text is untrusted: the app shows it nowhere but in its own dialog (as text), the Worker never interprets it as markup, and the maintainer's tools print it as data. Nothing is sent by a host whose person never opens the dialog.

Persistent keys never appear in request URLs: pairing uses the fragment, which is immediately removed from history. Relay capabilities are sent in the first WebSocket frame over TLS. The Worker does not log payloads.

Claude Code mod (docs/RICH_VIEW.md, "The Claude Code mod"; on whenever the rich view is on): the host ships a Claude Code plugin whose JavaScript runs inside Claude Code (2.1.287 and later) and loads it only in shells it starts, through `CLAUDE_CODE_PLUGIN_DIRS` in their environment (the person's own value is kept after it; nothing is written to Claude Code's settings or `~/.claude.json`; the plugin is copied to `<state>/claude-mod/<version>/`). The mod reaches the host over `<state>/mod.sock` (0600; a short path in a 0700 directory of the account when that is too long), a Unix socket that serves only the mod's five requests (hello, poll, result, event, switch), never a device and never the control socket's methods. It never listens and opens nothing: it asks the host what to do and does one of ten operations, all with the rights Claude Code's own prompt has (submit a message as the person's own words, `/model` and `/effort` with a plain argument, read the prompt's draft, read usage and the model, read the list of the agents Claude Code runs, queue a message for an agent, stop an agent or a run, interrupt a teammate, and, since mod version 7, call the `Workflow` tool to resume a run or run its script again); the host sends one only in answer to a device's `rich.send`, `rich.interrupt`, `rich.settings`, `rich.agent.*` or `rich.workflow.*`, which carry the device's `rich.*` rights as before, and the mod refuses any other operation. The `Workflow` call is a prompt whose first model request the mod answers itself with the call (the input is only the run's script path, an absolute `.js` of at most 1 KiB, and a `wf_…` run id; nothing else is passed), and the mod allows that one call, by the id it gave it, in Claude Code's permission check: the owner's confirmation on the device takes the place of Claude Code's launch question (a `tool.check` answer of a mod is the one Claude Code's permission check lets a mod give; whether a managed deny rule overrides it was not tested; on a Team-org account Claude Code's guard passes over it and decides alone). The interrupt refuses a teammate's running tool call and ends its turn, as Esc does; it names only an agent id of 4 to 80 plain characters. Every request carries the shell's session id and a token the host derives from a key of its own (`<state>/mod.key`, 0600) and that id; `hello` also checks, where the platform says (Linux, macOS), that the process behind the socket is one of that shell's. This stops a process that does not hold the shell's environment, and a Claude Code that is not the shell's (a nested one, another shell's); it does not stop a process of the same account that reads the shell's environment, which can already type into the shell and read the control socket. The token is never in a URL, a log or a published test. What the mod tells the host (turn start and end, usage, model changes, and Claude Code's own `SubagentStart`, `SubagentStop`, `TeammateIdle` and `Stop` events with an agent's id, type, last message cut to 400 characters and the list of background tasks, which the mod passes on to Claude Code unchanged) is checked and bounded before use. A model switch the host asked for is held for the device's answer for at most 22 s, then left to Claude Code's own question in the terminal; the person's own switches are never answered. A Claude Code without the mod (started before, `--bare`, `--safe-mode`, `disableAllHooks`, an organization's policy, before 2.1.287, or a startup file that dropped the variable) is driven through the terminal's keys as before, and the host reports which way each session goes (`state.controller`, `info.rich.mod`).

Signing in to Claude Code from the rich view (docs/RICH_VIEW.md, "Signing in"; on whenever the rich view is on): when the terminal shows Claude Code's sign-in (`/login`, or the login of a first start), the host reads the URL Claude Code prints (rows of its screen, joined) and sends it to the devices showing that tab, inside the same end-to-end encrypted channel as the rest of the view, as `state.screen` of `kind: "login"`. The URL holds no secret (an OAuth PKCE challenge and a state, valid for that one sign-in, which only the process that made them can finish); it is shown and opened only by the device's own browser (an https link, one the device validates first), never fetched, proxied or opened by the host or a third party, and the host does not log it. The authorization code the person is given after signing in is a secret: the card's field is masked, its value leaves the device once, inside one `rich.keys` request typed into Claude Code's own prompt, and is cleared from the field at once; the host does not put it in any state it sends, any log, the outbox, a draft, the history or the screen mirror (the sign-in card carries none), and its `rich.keys` result cache holds only the screen that followed. The terminal itself still shows what Claude Code echoes there, as any terminal text: the host's emulator and, with terminal history on disk, its saved screen hold that line like any other, and a device that shows the terminal sees it; sign-in codes are single-use and short-lived, but treat the terminal as you would the page where the code was given. Nothing about the account is read or stored by jaunt (the credentials are Claude Code's own files, which the host never reads for this).

Reloading a Claude Code session with the plugin (docs/RICH_VIEW.md, "Reloading a session with the plugin"; the device action `rich.reload`, device-only like `rich.send`, and the host setting "Restart idle Claude Code sessions to load the jaunt plugin", off by default): for a Claude Code that has no mod, the host types `/exit` into it and then, at the shell's prompt, a line made of `env` with the plugin's variables for that command only and the process's own arguments read from `/proc/<pid>/cmdline` (`ps` on macOS) with `--resume <session id>`. It is the same thing a person does by typing in that terminal, with the rights of `rich.send`, and the host closes neither the PTY nor the shell. It runs only when nothing can be lost (Claude Code idle by its registry, an empty prompt, no dialog, nobody typing, nothing running in the background that the process's end would kill: shells, agents, teammates, monitors, workflows) and only when every word of the original command line is a flag of Claude Code the host knows with the words it takes; a word it cannot place (a prompt, an unknown flag) refuses it, so that no text of the original line is sent twice. It never runs on a tmux shell or on Windows, and a session that did not get the plugin from a reload is not reloaded again.

Resuming a Claude Code conversation that ended in a shell (docs/RICH_VIEW.md, "A session that ended"; the device action `rich.resume`, device-only like `rich.send`): the host types `claude --resume <id>` at the prompt of that shell, as a person does. Nothing is typed unless the shell is alive with nothing running in front of it, the id is a conversation of Claude Code's own that this machine keeps (a transcript under its projects folder, a plain word that cannot read as an option), the shell is in the folder that conversation ran in, and the prompt waits (the same check as a session started from the top bar). It is the person's tap, never a program's: a service identity cannot reach it. A command the person had half typed at that prompt before would be completed by it, as in a reload.

Sessions history (docs/WORKSPACE.md "History", docs/PROTOCOL.md "Sessions history"; host/jaunt/history.py): the host lists the Claude Code and Codex conversations of its own disk to its paired devices and the desktop app on its computer, end to end encrypted like the session list. It reads Claude Code's transcripts (`<config>/projects/*/<id>.jsonl`: the first and last 64 KiB of a file over 1 MiB, the whole of a smaller one, never a line still being written; `<id>/custom-title.json`), its session registry (which sessions run), Codex's state database (opened read-only), its rollouts, `session_index.jsonl` and the writer locks of its threads (in `/proc/locks`, which run). What reaches a device of a session is its title (a name given to it, a title the runtime generated, or a prompt cut to 120 characters, which is the person's own text), folder, branch, times, size, number of prompts, where it was started and the options it resumes with; the full-text search (`history.search`) and the read-only view of a past conversation (`history.read`) send the person's and the model's words, like the rich view. Nothing of it is logged (the host's log names the runtime, the first 8 characters of an id and counts), notified or kept by a device (nothing for a machine that is not connected; a device keeps only its display choices, in local storage), and the web client renders it as text. The host keeps `<state>/history/index.json` (0600: per file what was read of it, the titles and the first and last prompt as titles included; only while "Keep terminal history on disk" is on, else in memory) and `<state>/history/launches.json` (0600: for each conversation a jaunt shell ran, the options its program was started with, read from its command line in `/proc` or from the line a launch typed, never a prompt nor the options that pick or name a conversation; a secret given as an option, which jaunt already advises against, would be kept there and typed again at a resume: keep secrets in the program's configuration). Hidden sessions and pinned folders are marks in `host.json`. Writes, all from a paired device's request (never a linked host, an AI session or a service): resuming opens a shell in the session's own folder and types the runtime's resume command with those options, as a launch from the top bar does (Enter included, which a device could type itself; nothing is ever typed again); renaming a closed Claude Code session appends the two lines Claude Code's `/rename` writes to its transcript and writes `<id>/custom-title.json`; deleting one removes for good its transcript, its folder, its file history, its environment and its uploads, and rewrites `history.jsonl` (the prompt history of every Claude Code session) without its lines: under Claude Code's own lock folder for milliseconds, by a temporary file and a rename, the lines other sessions appended meanwhile copied as they are; nothing is removed through a symbolic link. Codex's rename, archive, unarchive and delete are Codex's own (`codex app-server` on stdio, started for the request with the host's environment). Renaming, deleting and archiving are refused while the session runs (outside jaunt too) or a tab holds it. Agents: an AI session in a jaunt shell, with the switch of `jaunt_sessions` on (`typeLocal`, or `typeRemote` for a linked machine's), and a service with `observe` (`agents.history`) get the list of **closed** sessions only (title, folder, branch, last activity, id, where started), each marked closed; they cannot resume, rename or delete one through it. A service's `agents.resume` is its own right (below) and wakes a session with the options kept here, the same ones a person's Resume types, and no others.

Acting on agents and teammates (docs/RICH_VIEW.md, "Acting on agents and teammates"; device actions `rich.agent.send`, `rich.agent.stop`, `rich.agent.stopall` and `rich.agent.deliver`, device-only like `rich.send`, so a device without control rights only watches): writing to an agent and stopping one or all go through the mod's two operations `agentSend` and `agentStop` (an agent id of letters, digits, `_` and `-`, a message of 16 KiB at most, the mod refusing anything else); no key is typed. A message to an agent is never sent again by the host after an answer is lost.

OpenCode (docs/RICH_VIEW.md, "OpenCode"; docs/AGENTS.md "OpenCode sessions"; Linux hosts for the rich view): jaunt starts nothing of OpenCode's and writes nothing to its configuration or data. On a machine that has an `opencode`, jaunt shells have a second launcher on their `PATH` (`<state>/rich/bin/opencode`, a POSIX `sh` script, as Codex's: the real `opencode` runs with its arguments unchanged outside a jaunt shell, for every subcommand, and for a TUI given its own `--port`, `--hostname` or `--mdns`). Inside a jaunt shell it adds (1) while the host wants jaunt's tools in the runtimes, OpenCode's own inline configuration variable `OPENCODE_CONFIG_CONTENT` with the content of `<state>/bridge/opencode.json` (0600; the `jaunt-bridge` MCP server, the same wrapper and state path as for the other runtimes, and `permission: {"jaunt-bridge_*": "allow"}`, so that OpenCode does not ask again for tools that ask the owner themselves, as the allow rules jaunt adds to Claude Code's settings do; a variable the person set is left as it is), and (2) with the rich view on, for the interactive TUI, `--port 0 --hostname 127.0.0.1` and, unless the person set one, `OPENCODE_SERVER_PASSWORD`, 192 random bits from `/dev/urandom`. The TUI then also offers OpenCode's HTTP API (the one its documented SDK and `opencode attach` use, which can run commands and read files as the account) on a loopback TCP port, protected by OpenCode's own basic authentication with that password: a stranger, a program of another account or a web page that reaches the port without it gets `401`. What can read the password: the TUI's environment, which only the account reads (`/proc/<pid>/environ`), and the commands and programs OpenCode itself starts (it passes its environment to the commands its tools run, observed), which the account's agent could already run as the account. The host finds the port by looking, only for a process in front of a jaunt shell that is named `opencode` (or `opencode.exe`, its npm package's file): the loopback ports that process itself listens on (its own socket descriptors and `/proc/net/tcp`; a port on another address is never taken) and two variables of its environment (`OPENCODE_SERVER_PASSWORD`, `OPENCODE_SERVER_USERNAME`), kept in memory only, never logged and never sent to a device; no notice from the launcher is trusted. Before each action it checks again that the process still runs and still listens on that port, so nothing, the password included, goes to a port another program took. It reads the conversation of the TUI only from that server (`GET /session/{id}/message`, the event stream and the lists of sessions, permissions, questions, models, agents and commands: end to end encrypted to the devices that show the view, nothing written to disk), never OpenCode's database or files. The actions are a device's (paired devices only, never a linked host or an AI session; a service such as AgentsWorld only under its `answer` right): a message (`POST /session/{id}/prompt_async` or `/command`, with images as data URLs; a new conversation `POST /session` and `POST /tui/select-session`), Stop (`POST /session/{id}/abort`), an answer to a permission or a question exactly as the person chose it on a device (`POST /permission/{id}/reply` with `once`, `always` or `reject`, with the person's own message when they gave one; `POST /question/{id}/reply` or `/reject`; first answer wins with the terminal, and the host never answers by itself), and renaming the conversation with the tab (`PATCH /session/{id}`). *Allow always* is OpenCode's own, kept in its memory until it exits (nothing appeared in its saved permissions, observed with 1.19.5) and shown with the patterns it allows; jaunt saves no rule. The model, variant and agent the view chooses apply to the messages it sends only. Each action is executed at most once per operation id and never replayed after a reconnection; nothing is typed into the terminal. A TUI started without the launcher, on a host that cannot look into `/proc` (macOS, Windows), or against a server on another address is not reached: the view says so and the terminal is where it is used.

Rich view parity (the terminal's own dialogs, drafts, modes and completion from the view): the host reads the bottom of its own copy of the shell's screen (the emulator it already keeps for replay) and sends a plain-text copy of that region (40 lines at most) and what it recognizes there to the devices showing the view, end to end encrypted like terminal output; nothing of it is written to disk. A device may then press keys in that terminal (`rich.keys`: a fixed list of named keys, or printable text with every control character and line break removed, typed key by key or sent as one bracketed paste, so Enter is always a key the person pressed): only a paired device (never a linked host or an AI session; a service only under its `answer` right, below), only while the setting is on, only while the program in the shell's foreground is still the Claude Code or Codex instance the view follows (checked right before each key; before the runtime registers, the same foreground job), executed once per operation id and never replayed after a reconnection. A key meant for one dialog carries that dialog's screen id and is refused when the terminal shows something else; a card replaced by another question under the finger ignores taps for a moment. These keys are what a person at that terminal could type, with the same reach: a "don't ask again" option in a terminal dialog is shown with its label and chosen only when the person picks it, and since a dialog's letters and digits are its hotkeys (Codex's `p` writes a rule to its rules file), the card offers no free text field over a dialog with options unless the person asks for raw keys, which it says; an answer typed after choosing a text option goes as a paste, only into the runtime's prompt or that same question's field, never into a dialog that came up meanwhile. The screen reader finds the live prompt first, so a draft or a list in it is never offered as a dialog's options. A message starting with `!` runs in the runtime's shell mode, as it does when typed at that terminal. Keys go through the same write path as terminal input but never claim the terminal's size or active view. Moving a terminal draft into the view clears it with the runtime's own keys only after reading it on screen (Claude Code's Esc only while its registry, read right before each one, says idle, so a turn is never interrupted); a draft whose content the terminal shows only as a placeholder is never taken. Completion (`rich.complete`) lists, read-only, slash command and skill names with the `description` and `argument-hint` of their front matter (the first 8 KiB of each file, from the runtimes' configuration folders, the project's `.claude`/`.codex`/`.agents` folders and installed Claude Code and Codex plugins), and file and folder names under the runtime's folder (from `git ls-files --cached --others --exclude-standard` in a git work tree, so ignored files are left out as the TUIs do, with the folder's own `core.fsmonitor` and untracked cache turned off and no optional locks, so a repository's configuration never runs a command, even before the person trusted the folder; else a bounded walk that skips `.git` and `node_modules`); never a file's contents. Like the terminal itself, these names can include files such as `.env`: a device paired with the host can already list them in a shell. A one-line slash command or a `!` shell command sent from the view to an attached Codex is typed into its terminal like a message to a Codex without the launcher (a paste, then Enter once its composer shows it), only while the TUI jaunt's launcher reported still runs as the shell's program.

Services that observe and answer sessions (AgentsWorld, formerly AgentsHome, and any program that enrolls with a manifest; off by default, the host switch "Programs that observe and answer sessions"; docs/PROTOCOL.md "Service identities"): a program of the host's account enrolls once and receives a key of its own (256 random bits, returned once; the host keeps its SHA-256 in `host.json`, 0600, and never logs, journals or sends it; `jaunt agents enroll` writes it to a file of 0600). A program other than AgentsWorld declares a manifest when it enrolls: a title, a description, the rights it may be given (among observe, answer, resume, create, terminate and pages below; never exec, type or open, which stay an AI session's) and the topics it may follow. The manifest is what the program says about itself: the host checks its form only (one line of text each, bounded, known rights and topics, nothing else), so nothing proves who wrote it and any program can take any title. The trust anchor is the owner's approval on a paired device, which shows the manifest with the process that asked (its process id, program, script and folder, from the socket's peer credentials, on Linux only); the devices show it as text. The local control socket admits only processes of the host's own operating system account (0600 in a 0700 folder; on Windows, the key of a file only the account reads), so a service is a program of that account, which could already act as the account. A manifest grants nothing by itself: each right it declares starts at ask and is the owner's to give, like AgentsWorld's; it bounds what the program can ever be given until it enrolls again, which the owner approves again, shown what it holds now (a right it drops goes with what it was granted). Rates, cooldowns and request limits are the host's for every service, never set by a manifest. A program enrolled by manifest reaches this machine's sessions only, never a linked machine's. Revoking it drops its key and its manifest. Only a paired device allows an enrollment, raises a service's rights or answers its questions: the program asks on the local control socket, where it, or any program of the account, could otherwise answer for itself. The desktop app on the host's own computer reaches the host through that same socket: it shows these questions and may lower a service's rights (ask, block), and says that answering and trusting are done on a paired device (a phone, or a browser or another computer where the host is paired); a level set from a paired device while a question waits answers it (ResetDeck, by contrast, is only a claim, `service: "resetdeck"`, held in check by its command rules). This is a boundary between programs of the account only as far as the account's files are: whatever reads the program's key file (the account itself) can act as it, as whatever reads `host.json` can act as the host. The key opens a connection confined to the methods listed in the protocol: it receives no broadcast, and never runs a command, opens an agent shell, types as a requester, sends a bridge message, answers an approval or changes a setting; the only things it can start are sessions of the owner's own, through `resume` and `create` below, and the only thing it can end is such a session, through `terminate`. AgentsWorld's requester row (`AgentsWorld on this machine`) holds six rights, another program's those its manifest declares, ask by default, trust for 1 h, 24 h or always, or block, each journaled: `observe` gives what the devices see of the sessions (names, automatic titles, folders, programs, the AI session each runs, the rich view's conversations, questions and plans, the screen region the rich view reads, the messages between sessions, the native notifications the sessions' programs write (each terminal bell, OSC 9, 777 or 99 of any shell, with the title and text the program gave, without control characters and capped at 100 and 400 characters as the devices' notifications carry them, whatever the owner's notification switches: those decide what the host notifies the devices of, not what a session shows; a device's "details" choice for Web Push does not apply either, as it decides what a third-party push service relays, while the service receives them, as connected devices do, over the local socket or the host's own encrypted link; a program's notification is never invented from its output), the owner's pending approvals and the artifacts the sessions published: their list and, for one at a time, the page's HTML or the doc's Markdown, 1,500,000 bytes at most, which is as private as the conversation and arbitrary page code a service must not run in its own origin, apart from the files, assets and page data the host also keeps, which it does not give; the "Show Claude Code artifacts" switch still turns it off, each read is journaled once without its content, and change notices carry ids and metadata only; while it follows the summaries of every session, the host reads every Claude Code and Codex session's files as for an open view, every 2 seconds, and keeps nothing more than for a view); `answer` gives the rich view's own actions (answering permissions, questions and plans, keys in the terminal, messages, interruptions) under exactly the checks a device's go through, once per operation id, never replayed after a reconnection. `answer` is as strong as a person at the rich view: approving a permission lets the session run what it asked (a command, a file change), and "allow for this session" or a "don't ask again" option in a dialog widens that; trust it only to a program you trust with your sessions. `resume` lets the service start the owner's own Claude Code or Codex sessions: it names a session that already exists on the machine and the host opens a new tab, visible in every client like any other, in that session's own folder, running the options that session itself ran with and then the runtime's resume form (`claude [options] --resume <id>`, `codex [options] resume <id>`) and nothing else. This is the only service action that starts a process, so the service has no control over it: the id must match a transcript or rollout the runtime itself keeps under the owner's home, the folder comes from that record and never from the caller (a folder that no longer exists is refused), the command is built by the host from fixed parts and the session's own options (below) with no caller-supplied argument, option, folder, environment or name (such a request, a `model`, a `mode` or a `bypass` included, is refused, not ignored), a session already running in a tab is returned instead of started twice, and one session is woken at most once every 30 seconds. The options are the ones the session already had, never more, and the service neither sees nor changes them: the options its program was started with by a jaunt shell (`<state>/history/launches.json`, above) or, for a session started outside jaunt, what the runtime's own files record of it (Claude Code's permission mode, model and effort; Codex's approval policy, sandbox, model and effort), read by the same code as the history's Resume. A session that ran with `--dangerously-skip-permissions` (or `--yolo`) therefore wakes in bypass mode exactly as it ran, which is reusing its own settings and not an escalation by the service; a session that never ran in bypass mode cannot be woken in it through `resume` (bypass for a new session is what `create` below is for, and says so). The options are filtered once more before they are typed, so that a word that picks, names or starts a conversation, or that could be a prompt, is never typed even from an edited file; a secret given to the program as an option, which jaunt already advises against, is kept in that file and typed again (keep secrets in the program's configuration). Unlike the other two rights, ask mode asks for each session, naming it (title, folder, program, and the exact command with its options, bypass included) on a paired device, and an allowance covers that one session once; only a trust of 1 h, 24 h or always lets the service wake any of the machine's sessions without asking. A resumed session is a full Claude Code or Codex session with the owner's permissions, hooks and settings, in the permission mode it ran in, and with the conversation's earlier context: waking one can spend tokens and lets that session act on its folder, so trust it only for a program you trust with that. Every wake and every decision is journaled with the session, its folder, how many options it was woken with and where they came from (never the options themselves) and what happened, never more. `create` lets the service start new Claude Code or Codex sessions of its own choosing, and make folders to start them in. Plainly: with `create`, the service can start a session with any prompt in any existing folder of the machine, bypass mode included (`--dangerously-skip-permissions` for Claude Code, `--yolo` for Codex), in which that session runs commands and edits files without ever asking anyone; there is no separate right for bypass. `agents.create` names the program (`claude` or `codex`), an existing folder and, optionally, a prompt, a model, an effort, a mode (`default`, `acceptEdits`, `plan`, `bypass`) and a name; the host builds the command from fixed parts (the model is one word of a strict charset, the effort and mode are picked from fixed lists, the prompt is one word quoted for the tab's shell and placed after `--`, so it is never an option or a second command; no other argument, environment or folder rule is accepted: such a request is refused, not ignored), through the same launcher as the top bar's, so the Claude Code mod applies. A request is validated (folder exists, program installed, values legal) before the owner is asked; in ask mode each start asks on a paired device, naming the program, folder, mode (bypass called out plainly), model, effort and the beginning of the prompt, and an allowance covers that one start only; a trust of 1 h, 24 h or always covers every start and every folder, bypass included. At most six starts per minute; a retried `op` starts nothing twice. `agents.files.list` (under `observe`) gives only the folder names of a folder, never a file name or content; `agents.files.mkdir` (under `create`) makes one new folder whose parent exists, and `git init` in it when asked. Each start and folder is journaled with its program, folder, mode, model, effort and the length of the prompt, never the prompt. The session started is a full session with the owner's permissions: trust `create` only for a program you trust with that. `terminate` lets the service end the jaunt shell of a Claude Code or Codex session (like the tab's own close; the conversation stays in the runtime's own files and can be woken again with `resume`): it names a session, only a shell running one of those programs is accepted, ask mode asks for each session on a paired device naming the tab, folder and AI session id, and an allowance covers that one stop; a trust of 1 h, 24 h or always lets it stop any of them. Whatever runs in that shell stops with it, unsaved work included. `agents.rich.mode` and `agents.rich.settings` are under `answer`: they change a running session's permission mode and its model and effort (this session only, never the program's default) exactly as a person at the rich view does, so `answer` can move a session from `plan` to accept-edits (and, when the program offers it, to bypass). Every stop is journaled with the session and what happened. `agents.rich.image` (under `answer`) lets the service put an image in a session's message: the image is uploaded in chunks into the host's private image folder (`<state>/rich/images`, 0600, a name of the host's own, never a path the caller names; at most 20 MiB; only PNG, JPEG, GIF and WebP by their first bytes; a SHA-256 commit) and sent with the message through the rich view's image-by-path flow, as a device does; the message is submitted as `agents.rich.send` submits one, so an image can carry any text the service writes. In ask mode one question covers the whole upload. `agents.rich.complete` and `agents.git.diff` (under `observe`) read the session's folder as observing already does: file names below the session's folder for completion, and the text of the changes of its git repository (at most 40,000 bytes, below that folder only, a path that leads out refused, no file content outside the diff); git is run with the folder's own configuration kept from running anything (no external diff driver, text conversion, file system monitor, pager or prompt), but a diff shows the content of changed files, secrets in them included, so `observe` is as private as the folder. `pages` ("Write page data"; a manifest may declare it, AgentsWorld's holds it) lets the service write the documents of the pages the sessions published (`agents.artifacts.db`), which the pages open on the devices read live and act on as they were written to act, and which the publishing Claude Code session can read back (`jaunt_artifact_data`) as page data, untrusted; reading them is `observe`, and they are as private as the conversation. Writes go through the page runtime's own checks (path grammar, 256 KiB a document, 5,000 a page), at most 600 a minute per service whatever its level, and are journaled without their data; in ask mode the first write asks, "Allow this write" lets that one through, "Allow until restart" holds until the host restarts. The `artifacts.data` topic tells a service that a document of an artifact it named was written (which document, the operation, and whether a page, the session or a service wrote it), never the data. Its former name, `agentshome`, is accepted until 2026-11-01 as an identity of its own (its own key, rights and approval); enrolling the new name asks the owner again and copies nothing from it. Its actions are journaled once each, without the text of a message, an answer or a paste. Through the host's links the same program reaches the sessions of the linked machines: each of those machines sees it as a requester of its own (*host: <machine> · AgentsWorld*), behind its own switch, with its own six rights asked of its own owner on its own devices, and checks every request itself, whatever the requesting host or the program says; the requesting host only passes the request on once and never sends it again after a reconnection. A linked host must be trusted to name the service truthfully, as it is to name the Claude Code or Codex session asking (a host of the same owner, enrolled on the other with its own secret); it can never get more than these six rights in a service's name.

## Deployment

Use HTTPS/WSS outside loopback, set relay access keys and turn on `RELAY_KEY_REQUIRED`, rotate a key that may have leaked, give each tester their own invite and revoke it when they leave, keep `RELAY_ADMIN_KEY` in a password manager and, for Actions, in an environment restricted to `main`, restrict APP_ORIGIN to the exact Pages origin, enable MFA and branch protections, minimize Cloudflare/GitHub permissions, and monitor quotas and costs. Do not add third-party analytics scripts or extensions to the page. The static CSP blocks inline scripts and dynamic evaluation; dependencies are local. GitHub Pages cannot set every server security header; use a controlled domain/proxy for further hardening.

## This repository

It holds only the published web app, the releases devices download, and the GitHub Actions workflows that build and publish them from the private source. Those workflows start by hand, on a schedule or from one another, never from a pull request, a push or a comment. They check the source out with deploy keys: a read-only one, and one that may also write the release ledger and its tags, available only in the `ledger` environment. Android signing, relay deployment, relay administration and Pages deployment use environments restricted to `main`. Every action is pinned to a full commit hash, and no workflow keeps a cache. Workflow logs are public: they never print a secret, but they do show test and build output, which can include source file names and lines, and release notes name the source commit they were built from.

## Reporting a vulnerability

Use the repository's private vulnerability reporting channel when available. Never publish a key, QR code, confidential terminal log, host.json file, or vault export. Before public disclosure, the maintainer must establish a private reporting channel and rotation policy.

## Desktop boundary

The desktop renderer is sandboxed, with Node integration disabled and context isolation enabled. It receives a narrow preload IPC interface, validated against the application's main frame. Bundled resources are served through the secure `jaunt://app/` scheme; external navigation opens the system browser and never receives the host bridge. The relay also admits the exact native renderer origin `jaunt://app` for remote desktop connections; arbitrary browser origins remain rejected. Origin checks are not authentication: native clients still need routing capabilities and the host-authenticated encrypted handshake. The renderer's direct link is Chromium's own `RTCPeerConnection` (a data channel only); the app grants it no camera or microphone, so Chromium keeps hiding local addresses behind mDNS names. Local access uses the existing private Unix control socket and grants the same account privileges as the CLI. It is not a second network listener and does not bypass remote authentication.

The desktop release and host installer are part of the trusted update surface. Checksums detect corrupt/mismatched artifacts; they do not protect against a compromised repository/release publisher. The host's Python dependencies, direct and indirect, are hash-locked: each release's wheel carries a lock with the SHA-256 of every file PyPI serves for them (for every platform and Python the host supports), and the installers, so the updater, which runs the installer of the new wheel, install exactly those files (`pip install --require-hashes`), then the wheel without resolving anything else; a new release of a dependency reaches a host only once a jaunt release locks it. The few dependencies PyPI has no wheel of are built by the locked setuptools, never by one fetched for the build. uv, used only where no usable Python exists, is one pinned release checked against its SHA-256 before it runs (it checks the Python builds it downloads itself). The release build's tools and the relay probe's client are hash-locked the same way. Installing an older release that has no lock resolves its dependencies as before. Desktop packages contain only allowlisted application files and runtime dependencies, not host state or user profiles. Test-only renderer sandbox overrides must never enter production launchers.
