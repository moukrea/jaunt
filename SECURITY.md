# Security model — unaudited beta

jaunt provides a full shell under the host account. There is no filesystem sandbox or read-only role: an authorized device can act as that user. Do not run the host with privileges that remote devices do not need.

## What is protected

Commands, output, files, and clipboard data are encrypted between the browser and host. The relay sees network addresses, rooms, presence, packet sizes and timing, and ephemeral public keys. It does not hold pairing or device secrets. The channel is authenticated by a random 256-bit secret, with ephemeral ECDH and AES-GCM. The protocol specification is kept with the source, which is private.

The primitives come from cryptography and Web Crypto. **Their composition into this protocol is new and has not received an external audit.** Tamper/replay and interoperability tests do not replace an audit. Do not describe jaunt as certified, invulnerable, or ready by default for sensitive production environments.

## What is not protected

- A compromised browser, machine, or system account remains compromised.
- GitHub Pages serves code that can access secrets after unlocking: an attacker controlling this repository, the private source repository or the page can replace the JavaScript. End-to-end encryption does not protect against a malicious client update.
- Without a password, keys are stored unencrypted in IndexedDB, like a remembered session. A password/PIN encrypts them at rest; a short PIN remains vulnerable to offline guessing. Prefer a long passphrase.
- Locking stops connections and clears active views. It does not guarantee cryptographic erasure of browser RAM.
- Terminal replays, terminal output to clients that accept it, scrollback pages and download chunks are deflate-compressed before encryption, one independent stream per frame. The relay sees frame sizes; compression makes them depend on how repetitive the content is. Someone who can both inject text into a terminal or file and observe the relay's traffic could use that length side channel (CRIME-style) to test guesses about secrets shown next to it. Uploads, keyboard input and control messages are not compressed.
- A complete QR code grants shell access for ten minutes. Never put it in an issue, public screenshot, CI log, or analytics.
- Browser notifications are delivered through the browser's push service. Program-supplied notification titles and bodies are displayed and sent through that service; do not include secrets in notifications. Android follows system lock-screen privacy settings. Terminal output is not scraped for notifications.
- Relay access keys (Worker secret `RELAY_KEYS`, enforced by `RELAY_KEY_REQUIRED`) only decide which **new** hosts may register on the relay; they are not an authentication of hosts or devices, which remains the rooms' 256-bit capabilities and the end-to-end handshake. A key is a shared onboarding secret: anyone holding a valid one can register hosts on the owner's relay (and spend its quota) until the owner removes it; a room registered with a key of `RELAY_KEYS` stays registered after its removal (no per-room revocation for those). Rooms registered before enforcement are accepted by their capabilities alone. Hosts keep the key in `<state>/relay-key` (0600, outside `host.json`), send it only in the first WebSocket frame, never log it, and remove `jaunt_RELAY_KEY` from their environment so the daemon, its shells and their programs never inherit it. Pairing codes never contain it. The published configuration, installers and packages name no relay.
- Tester invites are per-person relay access keys that the relay creates and keeps as SHA-256 digests; a key is returned once, at creation, and never stored. They are managed through `POST /v1/admin/invites`, off unless the Worker secret `RELAY_ADMIN_KEY` is set, which it compares in constant time; the API accepts only POST with a bearer key, refuses requests carrying an `Origin`, has no CORS and logs nothing. Whoever holds `RELAY_ADMIN_KEY` can create keys that register hosts, list testers' names and the room ids their invites registered, and revoke or forget those registrations; it gives no access to any host or device (room capabilities and the end-to-end handshake are unchanged). A leaked invite key registers at most its host limit before the owner revokes it. Forgetting the rooms of a revoked invite deletes only registrations that record that invite, closing their connections (4004); anyone who then presents a valid key and knows such a room id could register it with their own capabilities, which denies service to the old host but reaches none of its devices, whose end-to-end handshake needs the host's pairing secrets. The owner's script never follows redirects (it would resend the admin key) and never puts a key in a URL. In GitHub Actions, whose logs and summaries are public on this repository, the workflow prints neither keys nor tester names: create and list are encrypted with age to `OWNER_PUBLIC_KEY` or refused before anything is created. Workflow inputs are run metadata, not secrets.
- A revoked device can no longer authenticate to the channel, but knows the previous shared routing capability. It may still disrupt relay availability until the host identity is rotated. Routing secrets are not a complete quota or anti-DDoS system.

## Shared GitHub Pages origin

Sites at `moukrea.github.io/another-project/` and `moukrea.github.io/jaunt/` share a browser origin. Another vulnerable project on that origin could target jaunt's storage. Paths are not a security boundary. For sensitive use, serve jaunt on a dedicated origin (its own domain/subdomain) and pair again there. A PIN protects keys at rest but does not replace origin isolation or trust in the JavaScript being served.

## Storage and permissions

`~/.local/share/jaunt/host.json` and the control socket are private to the current account. The directory uses mode 0700, state uses 0600, and writes are atomic. `attachments/` contains uploaded files; locking the app does not delete them. Remove unneeded attachments through the file browser.

On Windows the local control channel is a loopback TCP port instead of a 0600 Unix socket: any process of any account can connect to it, so every request must carry the random key in `%LOCALAPPDATA%\\jaunt\\control.json`, which only the account (and administrators) can read through the profile's ACL. The state directory relies on that ACL rather than POSIX modes.

Artifacts: a page Claude Code publishes from a jaunt shell is copied to `<state>/artifacts/` (0600) and sent to the account's paired devices. It is arbitrary HTML and JavaScript, so the clients never render it in jaunt's origin: it runs in `artifact.html` inside a sandboxed frame without `allow-same-origin` (an opaque origin with no access to jaunt's storage, keys, cookies or window), under that page's own policy (inline code and the cdnjs, jsDelivr, unpkg, Tailwind play CDN, jQuery and Google Fonts libraries claude.ai admits for artifacts, and `blob:` URLs the frame makes itself; no other script or connection). The frame may run forms (handled in script; `form-action 'none'`). jaunt's own UI still loads no CDN script. The claude.ai runtime jaunt provides to those pages (`claude.use`: db, user, artifact, downloads, permissions) is reached only by postMessage to the client, which binds every call to the artifact it shows: a page reads and writes its own documents and its own host copy, nothing else, and a file it offers is saved only through the device's normal save prompt. Files Claude Code uploads beside an artifact as assets (`Artifact` with `asset: true`; the page names them `/_blob/<id>`) are copied by the host from the local paths the tool reported, only for an artifact it already keeps, only regular files of media, font, PDF or text-data types that still match the uploaded SHA-256, into `<state>/artifacts/<id>.assets/` (0600, at most 64 MiB per artifact); the device fetches them over the encrypted channel and hands the bytes to the same sandboxed frame, which makes `blob:` URLs of them in its own opaque origin. They are as untrusted as the page and are removed with it. Its documents are page data, untrusted like the page: kept in `<state>/artifacts/<id>.db.json` (0600) and mirrored as `<stem>.jaunt-data.json` beside the page's source so the publishing Claude Code session can read them; pages should not store secrets there. Its hooks in `~/.claude/settings.json` are a PostToolUse entry for the `Artifact`, `ArtifactData` and `ArtifactComments` tools only and a UserPromptSubmit entry; they only talk to the local host, and turning "Show Claude Code artifacts" off removes them. What they add to the publishing session's context includes documents pages stored, labelled as page data from people, not instructions: a page's data is as untrusted as the page. A claude.ai artifact link Claude posts, live, in the rich view of the tab on screen opens the pane on jaunt's copy of that artifact when that shell published it (the same sandboxed frame); a click on an artifact link in the rich view or a terminal offers "Open in jaunt" or "Open on claude.ai" (a new tab, `noopener,noreferrer`); jaunt itself fetches nothing from claude.ai.

Rich view (off by default; "Rich view for Claude Code and Codex"): while a device shows a tab running Claude Code or Codex as a conversation, the host reads, and never writes, that runtime's own files: Claude Code's session registry (`~/.claude/sessions/<pid>.json`), the conversation transcript (`~/.claude/projects/…/<id>.jsonl`), a plan file under `~/.claude/plans/` that a plan names when it carries no text of its own, and `~/.claude.json` for the usage it caches (only `cachedUsageUtilization` is kept); for Codex the thread lock held by the shell's process, the rollout (`~/.codex/sessions/…/rollout-*.jsonl`) and `~/.codex/session_index.jsonl` for the thread's name. It sends that conversation (messages, reasoning summaries, tool inputs and outputs, diffs) to the devices that open the view, end to end encrypted like terminal output. Nothing of it is written to disk by jaunt: the host keeps the last items of open views in memory, and devices cache none of it (their local storage keeps only which view each tab shows and the person's own unsent draft in each tab's message box, until it is sent or emptied; both are removed when the machine is forgotten). For Claude Code, the view can also act, only through Claude Code's own mechanisms and only from a paired device (never a linked host or an AI session): (1) while the setting is on, a `PermissionRequest` hook group in Claude Code's user settings (no matcher, `…/hook-claude rich`, removed when the setting is turned off; the person's own groups are never touched) sends each permission, question and plan to the host over the local control socket, which no peer can reach; the hook outputs a decision only when a person answered on a device, and nothing otherwise (Claude Code then asks in its terminal as usual; outside a jaunt shell, for another process or conversation, or with the host down, it returns at once). "Allow for this session" rewrites every suggested permission to `destination: "session"`, so nothing is saved to user, project or local settings, and the card says what it allows (a switch to accepting every edit included). (2) Messages, Stop and `/model`/`/effort` are keys typed into the shell's terminal, exactly as a keyboard would: the host types only when its own copy of the screen shows Claude Code's empty prompt (the live, bottom-most box, with the cursor in it) and its registry is not waiting for an answer, one action at a time per shell, and presses Enter after a paste only when, right before it, the same Claude Code still has the foreground and its prompt shows the pasted text: never into a dialog (whose option 1 an Enter would pick) and never into the shell after `claude` exited. An action is executed at most once per operation id and never replayed after a reconnection. A `/model` or `/effort` typed this way is saved by Claude Code as the person's default, which the view says. While the setting is on, the `statusLine` of Claude Code's user settings runs jaunt's wrapper `<state>/rich/jaunt-statusline`, a POSIX sh script (no interpreter, no network, no host call) that chains the person's own status line command, if any, with the same stdin, output and exit status; only `command` is replaced, the person's original object is kept in `<state>/rich/statusline.json` (0600) and on a comment line of the wrapper, and turning the setting off (or `jaunt service uninstall`) puts it back exactly; a status line the person sets meanwhile is adopted as the one to chain, never overwritten or wrapped twice. In a jaunt shell (a session id of `A-Z a-z 0-9 _ -` only) the wrapper also writes the status line JSON Claude Code sent to `<state>/rich/statusline/<jaunt session>.json` (0700 directory created by the host, 0600 file, temporary file then `mv`; nothing when the directory is absent). That JSON holds session metadata, not the conversation: session and prompt ids, the transcript, working and scratchpad paths, the conversation's title, model, effort, context and token counts, cost, prompt cache statistics, the account's rate limits, versions; no message, tool input or output. The host reads the file of the shell a device shows and sends the limits, effort, context window, cost and cache state to that device like the rest of the view; the file is overwritten at each refresh, removed within a minute of its shell ending, and all of them when the setting is turned off. Jaunt shells never inherit the Claude Code or Codex session identity of whoever started the host (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_PID`, `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_EXECPATH`, `CODEX_THREAD_ID`, `CODEX_SESSION_ID`); configuration such as `CLAUDE_CONFIG_DIR` and `CODEX_HOME` is kept. For Codex (Linux hosts only), jaunt shells have `<state>/rich/bin` first on their `PATH`; on a machine that has a `codex`, it holds jaunt's `codex` launcher script (elsewhere it is empty, so nothing named `codex` appears), which runs the real `codex` with the arguments unchanged unless the setting is on (the flag file `<state>/rich/codex-on`), the shell is a jaunt shell, the command is the interactive TUI and the interpreter it names still exists. Then it runs jaunt's launcher with Python in isolated mode (`-I`): the shell's current directory and its `PYTHONPATH`/`PYTHONHOME` never reach the interpreter, so typing `codex` in a repository never runs that repository's `.py` files (the bridge's hook and MCP wrappers run the same way). The launcher asks the host first, over the local control socket, whether it is the foreground job of the jaunt shell it names (a tmux pane, a program started from a jaunt shell, or a host that is not running gets the real `codex` as it is), then starts Codex's own `app-server` on a unix socket in a private directory (`$XDG_RUNTIME_DIR/jaunt-codex` or `/tmp/jaunt-codex-<uid>`, 0700, checked to be a real directory owned by the account; one socket per launch, never a TCP listener), with the shell's environment and directory, and runs the same TUI against it (`--remote`, no other argument). A detached watchdog, started with the app-server, stops it once the TUI exits or the launcher dies: it first interrupts any turn still running (so closing the tab or killing Codex stops the agent's tools as quickly as it would without jaunt), then SIGTERM, then SIGKILL after 10 s. The host accepts the launcher's notice only over the local control socket, from a process of that shell's foreground job, for such a private socket; a notice it refuses makes the launcher stop its app-server and run Codex as it is. It keeps only metadata of an attach (`<state>/rich/codex-attached.json`: session, socket, pids and their start times, the id of the thread on screen) and connects to it as a second client. It answers Codex's approvals and questions only with what a person chose on a device (first answer wins with the terminal), shows what an approval also grants (a command's additional network and file-system permissions, a file change's session-wide write root) and offers only refusals for a request carrying a permission it cannot show, never offers the decision that saves a permanent rule (`~/.codex/rules`), and passes a secret answer (`isSecret`) to Codex without logging or keeping it; a message or Stop from a device is `turn/start`, `turn/steer` or `turn/interrupt`, executed once per operation id. The model and effort change either the running thread only or, as the view says, Codex's defaults in its `config.toml`. The app-server's own output goes to `<state>/rich/codex-<pid>.log` (0600). Codex sessions not started that way stay read-only: nothing is sent to them. Images a person adds to a message in the rich view are this person's data: the device keeps an unsent draft's images in its IndexedDB (removed with the draft, and when the machine is forgotten); on Send they are uploaded through the transfer path into `<state>/rich/images/` (0700, files 0600, named after the transfer), checked (that directory only, a regular file, size, PNG/JPEG/GIF/WebP by content, the device's SHA-256) and removed once the send is over, whatever its outcome (a Codex turn's once it ends, or the attach ends; anything left after an hour, or at host start). For Claude Code the host puts each image on its own desktop clipboard and types Ctrl+V, as a person at that terminal would: the last image stays on that clipboard; a headless host refuses images instead of sending the text without them. The images a conversation already holds are read from the runtime's files on request (`rich.image`) and sent to the device end to end encrypted, kept in the host's memory only while fetched; neither side logs an image or writes one elsewhere.

To reopen shells after a restart, the host keeps `sessions.json` (each shell's name, directory, size and the id of the Claude Code or Codex conversation it ran) and, while terminal history on disk is on, `scrollback/<id>/screen.json.z` (its history lines and screen as text) next to the raw history, all 0600. Everything a shell printed can therefore stay on disk until the shell is closed; turn off "Keep terminal history on disk" to keep only names and directories, or "Reopen shells after a restart" to keep nothing. A reopened shell never runs anything by itself: a conversation's resume command is typed at the prompt and waits for Enter. On Linux the installer enables systemd lingering (`loginctl enable-linger`; set `jaunt_NO_LINGER=1` to skip it), so the host and its shells run from boot without a login session.

Persistent keys never appear in request URLs: pairing uses the fragment, which is immediately removed from history. Relay capabilities are sent in the first WebSocket frame over TLS. The Worker does not log payloads.

Rich view parity (the terminal's own dialogs, drafts, modes and completion from the view): the host reads the bottom of its own copy of the shell's screen (the emulator it already keeps for replay) and sends a plain-text copy of that region (40 lines at most) and what it recognizes there to the devices showing the view, end to end encrypted like terminal output; nothing of it is written to disk. A device may then press keys in that terminal (`rich.keys`: a fixed list of named keys, or printable text with every control character and line break removed, typed key by key or sent as one bracketed paste, so Enter is always a key the person pressed): only a paired device (never a linked host or an AI session), only while the setting is on, only while the program in the shell's foreground is still the Claude Code or Codex instance the view follows (checked right before each key; before the runtime registers, the same foreground job), executed once per operation id and never replayed after a reconnection. A key meant for one dialog carries that dialog's screen id and is refused when the terminal shows something else; a card replaced by another question under the finger ignores taps for a moment. These keys are what a person at that terminal could type, with the same reach: a "don't ask again" option in a terminal dialog is shown with its label and chosen only when the person picks it, and since a dialog's letters and digits are its hotkeys (Codex's `p` writes a rule to its rules file), the card offers no free text field over a dialog with options unless the person asks for raw keys, which it says; an answer typed after choosing a text option goes as a paste, only into the runtime's prompt or that same question's field, never into a dialog that came up meanwhile. The screen reader finds the live prompt first, so a draft or a list in it is never offered as a dialog's options. A message starting with `!` runs in the runtime's shell mode, as it does when typed at that terminal. Keys go through the same write path as terminal input but never claim the terminal's size or active view. Moving a terminal draft into the view clears it with the runtime's own keys only after reading it on screen (Claude Code's Esc only while its registry, read right before each one, says idle, so a turn is never interrupted); a draft whose content the terminal shows only as a placeholder is never taken. Completion (`rich.complete`) lists, read-only, slash command and skill names with the `description` and `argument-hint` of their front matter (the first 8 KiB of each file, from the runtimes' configuration folders, the project's `.claude`/`.codex`/`.agents` folders and installed Claude Code and Codex plugins), and file and folder names under the runtime's folder (from `git ls-files --cached --others --exclude-standard` in a git work tree, so ignored files are left out as the TUIs do, with the folder's own `core.fsmonitor` and untracked cache turned off and no optional locks, so a repository's configuration never runs a command, even before the person trusted the folder; else a bounded walk that skips `.git` and `node_modules`); never a file's contents. Like the terminal itself, these names can include files such as `.env`: a device paired with the host can already list them in a shell. A one-line slash command or a `!` shell command sent from the view to an attached Codex is typed into its terminal like a message to a Codex without the launcher (a paste, then Enter once its composer shows it), only while the TUI jaunt's launcher reported still runs as the shell's program.

## Deployment

Use HTTPS/WSS outside loopback, set relay access keys and turn on `RELAY_KEY_REQUIRED`, rotate a key that may have leaked, give each tester their own invite and revoke it when they leave, keep `RELAY_ADMIN_KEY` in a password manager and, for Actions, in an environment restricted to `main`, restrict APP_ORIGIN to the exact Pages origin, enable MFA and branch protections, minimize Cloudflare/GitHub permissions, and monitor quotas and costs. Do not add third-party analytics scripts or extensions to the page. The static CSP blocks inline scripts and dynamic evaluation; dependencies are local. GitHub Pages cannot set every server security header; use a controlled domain/proxy for further hardening.

## This repository

It holds only the published web app, the releases devices download, and the GitHub Actions workflows that build and publish them from the private source. Those workflows start by hand, on a schedule or from one another, never from a pull request, a push or a comment. They check the source out with deploy keys: a read-only one, and one that may also write the release ledger and its tags, available only in the `ledger` environment. Android signing, relay deployment, relay administration and Pages deployment use environments restricted to `main`. Every action is pinned to a full commit hash, and no workflow keeps a cache. Workflow logs are public: they never print a secret, but they do show test and build output, which can include source file names and lines, and release notes name the source commit they were built from.

## Reporting a vulnerability

Use the repository's private vulnerability reporting channel when available. Never publish a key, QR code, confidential terminal log, host.json file, or vault export. Before public disclosure, the maintainer must establish a private reporting channel and rotation policy.

## Desktop boundary

The desktop renderer is sandboxed, with Node integration disabled and context isolation enabled. It receives a narrow preload IPC interface, validated against the application's main frame. Bundled resources are served through the secure `jaunt://app/` scheme; external navigation opens the system browser and never receives the host bridge. The relay also admits the exact native renderer origin `jaunt://app` for remote desktop connections; arbitrary browser origins remain rejected. Origin checks are not authentication: native clients still need routing capabilities and the host-authenticated encrypted handshake. Local access uses the existing private Unix control socket and grants the same account privileges as the CLI. It is not a second network listener and does not bypass remote authentication.

The desktop release and host installer are part of the trusted update surface. Checksums detect corrupt/mismatched artifacts; they do not protect against a compromised repository/release publisher. Desktop packages contain only allowlisted application files and runtime dependencies, not host state or user profiles. Test-only renderer sandbox overrides must never enter production launchers.
